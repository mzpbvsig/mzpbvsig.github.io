Claude Code 完整开发流程 · 最佳实践

以 Anthropic 官方 best-practices 为骨架（标 官方逐字 的句子是原文引用），补充 spec-driven 实践。核心要回答的问题："执行→更新状态→测试→提交"之后还有什么？ —— 有，提交只是单 task 内循环的结束，外面还套着收口/验证关。

官方逐字 实践补充 看场景可省 大功能才用
一句话先记住：你做的「实现 → 更新状态 → 测试 → 提交」是 单 task 内循环；它外面还有一层 收口：全功能做完 → 换干净上下文 subagent 复查 diff → PR / 人工 gate → CI/CD → 合并 → 清理。单人小改动到提交就够；进了分支/PR/团队，收口不能省。

实践补充0 · 一次性准备（配好就一直省事）

  • CLAUDE.md：/init 生成；只放"删了 Claude 就会犯错"的东西（命令、风格、PR 约定）。官方逐字 "only include things that apply broadly."
  • hooks：pre-commit 跑测试/lint/类型检查——确定性地每次执行。官方逐字 "hooks are deterministic and guarantee the action happens."
  • 权限 / auto mode：claude --permission-mode auto 让分类器放行常规、拦截风险，少点确认。
  • skills / subagents / MCP / gh CLI：领域知识、隔离上下文的专职 agent、外部工具接入。

大功能才用1 · 起步：访谈 → SPEC.md → 全新会话

功能大、不确定怎么做时，先让 Claude 面试你，把答案写成自包含的 SPEC.md，再开新会话用干净上下文执行。

I want to build [brief description]. Interview me in detail using the AskUserQuestion tool. Ask about technical implementation, UI/UX, edge cases, concerns, and tradeoffs. Keep interviewing until we've covered everything, then write a complete spec to SPEC.md.
官方逐字 "Once the spec is complete, start a fresh session to execute it. The new session has clean context focused entirely on implementation."

好 spec 的标准（官方）：点名涉及的文件与接口、写明不做什么、结尾给一个端到端验证步骤。

官方逐字2 · 主循环：官方四阶段

"The recommended workflow has four phases: Explore → Plan → Implement → Commit."
① Explore（plan mode） read /src/auth and understand how we handle sessions and login └ 只读不改，先搞清现状 ② Plan（plan mode） What files need to change? ... Create a plan └ 出详细计划；按 Ctrl+G 打开计划手改 ③ Implement（默认模式） implement... write tests... run the test suite and fix any failures └ 进入「单 task 内循环」逐条落地（见下） ④ Commit（默认模式） commit with a descriptive message and open a PR
什么时候跳过 plan？官方逐字 "If you could describe the diff in one sentence, skip the plan." typo、加日志、重命名这类直接做。

官方逐字 + 实践补充3 · 单 task 内循环（你现在做的那圈）

实现一个 task → 更新 tasks.md 状态 [ ] → [x] → 跑测试 → 提交（触发 pre-commit hook：测试 / lint / 类型检查） └ 失败 → 驳回提交，agent 看到报错 → 自我修正 → 再提交 ※ 每 3–4 个 task：做一次阶段性 code review
  • 纪律：先更新 spec/状态，再合代码（保证可追溯，便于审计与生成测试）。实践补充
  • 一 task 一 commit，回滚成本最低。实践 "Single task = one commit for easy rollback."

TDD 变体（官方称"最强模式"）

写测试 → 跑确认失败 → 提交失败的测试(checkpoint) → 实现到全绿（不准改测试）→ 提交
官方逐字 "test-driven development (TDD) [is] the single strongest pattern for working with agentic coding tools."

先提交失败测试 → diff 能暴露 Claude 是否偷改了测试来"作弊"过关。

官方逐字4 · 收口 / 验证关（"提交"之后真正还有的步骤）

官方有专门一节 "Add an adversarial review step"——这就是单 task 循环覆盖不到、最该补的一步。

"Before treating a task as done, have a subagent review the diff in a fresh context and report gaps."
"A reviewer running in a fresh subagent context sees only the diff and the criteria you give it, not the reasoning that produced the change, so it evaluates the result on its own terms."
ⓐ 对抗式复查 /code-review（看当前 diff 找 bug） 或自写： Use a subagent to review the diff against PLAN.md. Check every requirement is implemented... Report gaps, not style. └ 关键：做代码的 Claude 不给自己打分，换干净上下文 subagent ⓑ 开 PR → reviewer agents（安全/架构/最佳实践）→ 打回自动修订 / 合并 ⓒ 人工 gate → human review 最终批准 → 触发 CI/CD ⓓ 合并清理 → 删 worktree / 删分支 → /clear 进下一个任务
为什么必须做：单 task 测试全绿 ≠ 合在一起没破坏别处。整分支 diff 复查 + 人工 gate 专抓跨 spec 回归，这是逐 task 验证永远碰不到的盲区。
别过度：官方逐字 "A reviewer prompted to find gaps will usually report some, even when the work is sound... Tell the reviewer to flag only gaps that affect correctness or the stated requirements." 否则会过度抽象、加防御代码、为不可能的情况写测试。

贯穿全程的两条铁律

铁律官方逐字怎么落地
① 给 Claude 能自己跑的验证 "Give Claude a check it can run... the loop closes on its own." 三档强制力：同一 prompt 里跑 → /goal 条件每轮复检 → Stop hook 硬门（不过不阻塞收尾，8 次后放行）
② 狠管上下文 "Use /clear frequently between tasks." 任务间 /clear；同一问题纠正超过 2 次 → /clear 重开换更好 prompt；大功能写 SPEC.md 后开新会话

怎么用它对齐需求（按场景选深度）

场景走到哪一步能省什么
单人 · 一句话能描述的小改跳过 plan，直接 ③→④ 提交省 plan、省 SPEC、省正式收口
单人 · 一个中型功能plan mode 全 4 阶段 + 单 task 循环 + /code-review可省正式 PR/人工 gate（但复查别省）
大功能 / 不确定怎么做访谈→SPEC.md→新会话→4 阶段→收口全套不省
团队 / 进分支 PR全套到 CI/CD + 人工 gate收口一步都不能省
结论："执行→更新状态→测试→提交"是单 task 内循环，外面还套着收口层（换干净上下文复查 diff → PR → 人工 gate → CI/CD → 合并 → 清理）。小改动到提交就够，进了分支就不能省；而且官方明确——复查必须换干净上下文的 subagent，写代码的 Claude 不能验自己。
