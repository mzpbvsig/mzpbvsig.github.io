① 不跟 agent 对话,跟 loop 对话

你转述的:"让 loop 替我来 prompt" —— 核对结果:✅ 属实,是 Boris 最核心的范式转变
官方逐字
"我已经不再给 Claude 写 prompt 了。我跑的是一堆 loop,是它们在 prompt Claude、在决定该做什么。我的工作是写 loop。" "I don't prompt Claude anymore. I have loops running. They're the ones prompting Claude and figuring out what to do. My job is to write loops." —— Boris Cherny,转引自 Product Market Fit · 同句被 Digg 报道
实践补充 怎么理解"写 loop 而不是 prompt"

一条 prompt 给你一次性的输出;一个 loop 给你会复利累积的操作。loop 就是一个"壳":它自己去发现"有哪些活要干"→ 把一块丢给 agent → 检查 agent 交回来的东西 → 再循环。人不再是步骤之间的"连接组织",你写的是那个"替你去写 prompt 的东西"。

Claude Code 里把它产品化成了三档,按"要跑多久"区分:

  • /loop —— 本地循环,最长跑 3 天,按间隔重复跑你的 prompt。典型:盯 PR、自动修构建、Slack 摘要、盯部署。
  • /schedule —— 云端任务,关掉笔记本也在跑,可无限期。Anthropic 内部用它自动修 CI、自动更新文档。
  • /goal —— 一直跑到"条件满足"为止(社区叫"内置版 Ralph loop"),例:/goal all tests in test/auth pass and lint is clean。
看场景可省 "人力不足"是故意的

Boris 提到一个组织策略:给 4 人量的项目只派 2 个工程师。这种刻意的人手紧缺,逼着大家去搭 loop 和自动化,把预算从人力挪到 token 消耗上。这是团队管理视角的延伸,个人用不一定照搬。

② 从 4.6 起不用 plan mode,全开 auto mode

你转述的:"从 4.6 起就不用 plan mode 了,全开 auto mode" —— 核对结果:✅ 几乎逐字属实
官方逐字 弃用 plan mode
"以前是 plan mode,我现在不用那个了,我用 auto mode……新的模型其实不需要一个单独的规划步骤。它对 Opus 4 到 4.5 非常重要,但从 4.6 开始、到 4.7 就更是如此——它根本不需要了。" "What it used to be is plan mode. I don't use that anymore. I use auto mode... The newer models don't actually need a planning step. It was really important for Opus 4 through 4.5, but starting with 4.6, and definitely with 4.7, it just doesn't need it." —— Boris Cherny,《Reflecting on a year of Claude Code》(2026-06-08),整理见 howborisusesclaudecode.com
官方逐字 为什么 auto mode 反而更"安全"
"auto mode 比逐条读权限提示更安全,因为它让你只盯最重要的那件事。" "Auto mode is more safe than reading every single permission prompt because it means you're only paying attention to the most important thing." —— 同上。配套那句:"当你 99% 的请求都点同意,你的眼睛就麻木了 (your eyes glaze over)。"

实践补充 auto mode 的机制:每个动作不是丢给人审,而是过一个分类器判断风险;Anthropic 用上千份 transcript、红队测试、prompt-injection 评测做过加固。它是介于 default(逐条手批)和 bypassPermissions(完全不查)之间的中间档。

实践补充 入口:CLI 里 Shift+Tab 在 plan → auto → normal 之间循环;桌面/VSCode 用下拉选。

③ 不做 prompt engineering,也不做 context engineering

你转述的:"给模型最精简的必要上下文和工具,让模型自己探索" —— 核对结果:✅ 属实,Boris 称之为"context minimalism(上下文极简)"
实践补充 三个时代的演进(Boris 的原话框架)
Sonnet 3.5 时代prompt engineering
精雕 prompt
Opus 4 时代context engineering
精心喂上下文
现在context minimalism
给最少,让它自己找
官方逐字
"你给它尽可能精简的 system prompt、尽可能精简的工具,然后让模型自己把事情想明白。" "You give it the minimal possible system prompt, the minimal possible tools, and then you let the model figure it out." —— Boris Cherny,同视频
"只告诉模型它需要知道的,剩下让它自己搞定。你给它太多上下文,就等于在微管理它。" "Tell the model only what it needs to know and let it figure it out. When you give the model too much context, it's like you're micromanaging it." —— Cat Wu,同视频
看场景可省 / 注意边界

"极简"不等于"含糊":目标要说清,省的是中间的微步骤。做法是给一个精炼的任务说明 + 一条让它能自己取上下文的路(文件、搜索、MCP),而不是把一大坨上下文和工具列表一次塞满。

④ 一半工程在手机上完成,走路时语音对话

你转述的:"一半的工程在手机上完成,走路时和 agent 语音对话" —— 核对结果:✅ 方向属实(手机 + 语音 + 远程是核心工作流);"一半"这个比例是社区转述,未见 Boris 给出确切数字
实践补充 Boris 的移动工作流由三块拼成
  • 手机 App 直接写:Claude Code 有原生 iOS/Android App,带完整 Code tab,Boris "很大一部分代码是在 iOS App 上写的"。
  • 语音输入为主:Boris"大部分编码是对着 Claude 说,而不是打字"。CLI 用 /voice 然后按住空格;macOS 双击 fn 听写;iOS 用系统听写。
  • 远程触发 + 会话穿越:claude remote-control 能从手机把任务踢到你自己机器上跑;--teleport / /teleport 让同一会话在手机/网页/桌面/终端之间搬。Boris 在 /config 里"对所有会话开了 Remote Control"。
"离开工位、走着走着想到点什么,就从手机上踢起一个任务——Claude 在你自己机器上跑。" "Walk away from your desk, think of something, and kick off a task from mobile — Claude runs on your machine." —— Boris,整理见 howborisusesclaudecode.com

⑤ 视频里另外两条同等关键、但你没提的

既然要"到底怎么做",这两条是把上面四条串起来的关键,值得一起记
官方逐字 错误不要重新 prompt,要写进 CLAUDE.md
"每次 Claude 犯错,我不会告诉它换个做法。我会让它把这条写进 CLAUDE.md,或者做成一个 skill。能做到这点,Claude 就能一直跑下去。" "Every single time Claude makes a mistake, I don't tell it to do it differently. I tell it to write it to the CLAUDE.md, or make a skill, or something. If you can do this, then Claude can just run forever." —— Boris,同视频

实践补充 为什么这条是 loop 能成立的前提:对话里纠正 = 一次性补丁;写进 CLAUDE.md/skill = 对所有未来运行的永久修复。错误率持续往下走,同样的错不再复发,loop 才敢长期无人值守地跑。这正是 ① 的地基。

官方逐字 最重要的一条:给 Claude 一条"自我验证"的路
"想从 Claude Code 拿到好结果,最重要的事大概就是:给 Claude 一个验证自己工作的方法。有了这个反馈回路,最终结果质量会翻 2–3 倍。" "Probably the most important thing to get great results out of Claude Code — give Claude a way to verify its work. If Claude has that feedback loop, it will 2-3x the quality of the final result." —— Boris(其 #1 tip),整理见 howborisusesclaudecode.com

实践补充 验证方式按场景:跑 bash 命令、跑测试、浏览器测试(Claude 的 Chrome 插件)、模拟器。"会自检"是 auto mode 敢全开、loop 敢长跑的另一半地基。

一句话总结他到底怎么做

Boris 把自己从"对话者"退成"系统设计者":先用 CLAUDE.md + skill 把"别犯这个错"固化成规则,再给 Claude 一条能自检的验证回路,然后把模型放进 auto mode 全自动跑,自己只写决定"干什么、干到什么程度"的 loop / schedule / goal——而这些指挥动作,很多是走在路上用手机语音、或远程踢到自己机器上完成的。

底层信念:模型已经强到不需要你精雕 prompt、不需要 plan mode、不需要堆上下文。你越微管理,越拖它后腿。你该做的是给最少的必要信息 + 一条取上下文的路 + 一条自检的路,剩下交给它。
