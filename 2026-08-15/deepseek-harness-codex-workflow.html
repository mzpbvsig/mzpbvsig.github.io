网页版的“本地能力”不是很有限吗？

是的——如果“本地能力”指直接访问开发者电脑。但 Codex 网页版做仓库任务时，浏览器主要是控制面板，真正执行代码的是隔离的 Codex Cloud 容器，不是网页 JavaScript，也不是你的本机。

1 · 浏览器控制面选择 GitHub 仓库和环境，提交任务，查看日志与 diff，继续追问或决定是否开 PR。浏览器本身不需要读取你的本地磁盘。
2 · 云端执行面每个任务启动隔离容器，checkout 指定 branch/commit，执行 setup，运行 shell，编辑代码并执行 lint、测试和构建。
3 · Git 交付面结果以 summary、diff、分支或 PR 返回；开发者评审后合并，或者把分支拉回本机继续处理。
4 · 本机补充面只有依赖本机文件、localhost、内网、硬件、原生 GUI 或个人浏览器状态的任务，才必须转到 CLI、IDE 或桌面环境。
OpenAI 官方逐字“Codex creates a container and checks out your repo at the selected branch or commit SHA.”Codex 会创建一个容器，并把仓库检出到选定的分支或 commit SHA。— OpenAI Docs · Cloud environments
官方能力边界

云端容器可以有完整终端，但不能天然拥有你的本机现场

官方文档说明：仓库可以为云环境配置依赖、工具、环境变量和 setup script；Agent 会循环执行终端命令、修改文件并验证结果。Agent 阶段的互联网默认关闭，可显式配置；环境也不是永久开发机，缓存只是用来加速后续任务。

因此它很适合“仓库里能复现”的工作，不适合直接操作你电脑中尚未提交的文件、正在运行的本地服务、VPN/局域网资源、USB 设备、系统原生窗口或私人浏览器登录态。来源：Codex cloud、Cloud environments。

对 DeepSeek Harness 的谨慎判断

codex/* 分支证明了 Codex 风格的交付痕迹，但不能证明使用的是网页版

公开 Git 历史能看到大量 codex/* 分支和 PR，仓库也把构建、测试与验证写成可脚本化命令和 CI，这些都与云端容器相容。可是分支名不会记录任务究竟从 Codex Web、CLI、IDE 还是其他自动化入口发起；公开材料也没有完整会话元数据，所以不能断言 DeepSeek 团队只用网页版。

仓库证据：package.json 的脚本入口、GitHub CI、真实 Web 流程验证 skill。

准确说法：网页版的直接本机访问有限，但云端编码能力并不只等于“浏览器能力”。它把仓库复制到可配置的云端开发容器里工作。DeepSeek Harness 这种大部分行为可由代码、终端命令和 CI 验证的项目，许多任务适合这种模式；机器相关的最后一公里仍要本地执行。

这张 Trajectory 截图具体说明了什么？

它展示的是 DeepSeek Harness 自己的 Web Client 连接到一个本地 Windows Host 后的完整执行轨迹。浏览器负责显示和交互；Host 负责文件系统、PowerShell、权限与工具执行。

1 · SYSTEM / CONTEXT

运行环境和权限会作为上下文动态注入模型

截图先显示工作目录为 Z:\Users\ZK\Desktop\wvp、文件策略为 workspace-write；随后又出现 approval 从 ask 改为 never，以及新的 danger-full-access runtime context。说明权限不是浏览器自己的权限，而是 Host 为当前 Agent 会话提供、并可在运行中更新的策略。

2 · TOOL pwsh → UNKNOWN_TOOL

模型第一次用了错误的调用协议

当前处于 Code mode。模型直接向协议层调用 pwsh，注册表返回 UNKNOWN_TOOL。这不代表本机没有 PowerShell，而是该模式没有把 pwsh 作为顶层 wire tool 暴露给模型。

3 · TOOL run_code

模型识别错误并切换到 Code Mode 的正确入口

它明确写出 “I need to call pwsh from inside run_code”，然后调用外层 run_code。说明这个失败是可恢复的结构化工具错误，当前 turn 没有因此终止。

4 · SUBTOOL pwsh

run_code 内部通过 Host binding 调用了本地 PowerShell

Trajectory 同时显示外层 run_code 和橙色的 SUBTOOL pwsh；PowerShell 返回目录内容，最终 Assistant 再整理成人类可读答案。这正是“外层程序编排多个宿主工具”的结构。

官方逐字“Under code it is the registry's only wire contribution; the other visible capabilities are declared in a generated SDK section.”在 code 模式下，注册表在协议层只暴露 run_code；其他能力通过生成的 SDK 声明，并由程序经 binding 调用。— DeepSeek Harness Tool Catalog
它能证明这个会话连接了能访问 Z:\ 路径的 Windows Host；Host 提供 PowerShell；Code Mode 通过 run_code → tools.pwsh 执行；Trajectory 会记录权限上下文、失败、外层调用和子调用。
它不能证明不能证明浏览器 JavaScript 直接读取磁盘；不能证明这是 Codex Cloud；不能证明 DeepSeek 团队用同一种入口开发仓库；也不能把可见 Assistant 文本等同于模型完整的隐藏思维链。
安全含义danger-full-access 表示文件操作绕过隔离；approval: never 则表示需要审批的请求直接被拒绝，并非自动批准。普通操作因已处于全访问模式通常无需升级；真正边界落在 Host、工具注册和策略组合上。
产品含义Trajectory 是调试与审计账本：不仅给最终答案，还能看见模型收到什么上下文、调用为何失败、怎样自我修正，以及哪个宿主工具真正产生结果。
一句话：这张图说明 DeepSeek Harness 的网页可以间接拥有很强的本地能力，条件是本机运行了 Host 并把文件系统、Shell 等能力作为受策略控制的工具提供给 Agent；能力来自 Host，不来自浏览器。

具体到一次任务：人下达以后会发生什么？

假设人给出一个任务：“限制每个会话可同时运行的后台任务数；超限时明确拒绝；补齐测试和文档。”下面按仓库现有规则，还原这个任务从输入到合并的实际时序。

0 · 人定义任务

输入不是只有一句需求，至少还要有验收边界

仓库的 Task 模板要求“一句话说明工作”，并在折叠区填写验收条件、交付物、测试证据。所以理想输入不是“优化后台任务”，而是明确要观察到什么结果。来源：Task issue template。

1 · 为任务隔离工作区

任务进入自己的 worktree 与分支

公开历史中此类任务通常出现在 codex/<task-name> 分支；正式规则明确要求“一条 PR 分支一个 worktree”，并禁止并行修复共用 checkout。这里可以确认隔离纪律；无法确认是人还是自动化创建了 worktree。来源：stacked PR review guide。

2 · Codex 先定位，不立即写代码

读取指令树、架构、目标包和现有测试

根 AGENTS.md 要求修改 packages/ 前先读架构文档；目录中的下级 AGENTS.md 再补充局部规则。Codex 会搜索相关服务、调用者、测试、README 与已有 Agent Note，确定行为应该落在哪个插件或接口上。

3 · 判断任务是不是“非平凡变更”

非平凡任务先建立或更新决策记录

如果会改变行为、架构、跨文件约定、测试策略、配置或协议，就要在同一个 PR 里新增或更新 Agent Note。实施前的 Note 包含 Problem、Proposal、Alternatives considered、Acceptance criteria 与 Risks；纯机械、小范围编辑可以跳过。仓库没有规定每个任务都必须进入 Plan Mode。

4 · 实现第一个可验证切片

实现、测试和所属文档一起改

Codex 修改最小的责任边界，同时补 owning test；如果变化会被用户、模型、CLI 或编辑器看到，还要更新 keyless snapshot 或真实示例。如果公共行为改变，README/JSDoc 与 Agent Note 同一批更新，而不是等最后补文档。

5 · 在本地形成短反馈循环

失败 → 读错误 → 修代码 → 重跑受影响检查

它不会默认每轮跑全仓。包行为跑定向 Vitest；模型或 UI 输出跑对应 snapshot；构建与导出变化跑 build/hygiene；真实 provider 行为在有凭证时跑 e2e。每项检查必须能对目标回归真正失败。

6 · 自审、提交与推送

先核对真实 base 和完整 diff，再发布分支

Codex/作者检查 branch、worktree 状态和 PR base，用 change-scope --base 看 committed、staged、unstaged、untracked 四层变更。pre-commit 处理暂存 lint、空白与元数据；pre-push 只跑增量 typecheck。更广的矩阵留给 CI。

7 · 创建或更新 PR

PR 必须告诉评审者“改了什么、怎么验证”

PR 模板要求关联 Issue，并填写“变更”和“验证”；解决型 PR 使用 Fixes #NN。普通 PR 活动会把关联 Issue 推进到 In progress，请求评审时进入 In review。来源：PR template与issue lifecycle policy。

8 · 评审不是终点，而是另一个循环

Changes requested → 回到实现 → 定向验证 → 再请求评审

每条意见先按技术事实核验，不是无条件同意。接受的修复落在最初引入问题的 PR，保留为独立 commit，再传播到上层 PR；改写分支历史后要重新检查未解决讨论、批准、mergeability 与 CI。自动化会把 Issue 从 In review退回 In progress。

9 · CI 通过并合并

本地证据与完整 CI 都成立后，任务才算完成

独立 PR 直接走正常合并；依赖 PR 先组成官方 stack，再自底向上合并。PR 关闭关联 Issue 后，生命周期自动进入 Done。最终保留的是代码、测试、Agent Note、文档和提交记录，不是整段 Codex 对话。

一句话时序：任务 + 验收 → 独立 worktree → 读规则与代码 → 必要时写 Agent Note → 小步实现 → 定向测试循环 → 自审并推送 → PR 评审循环 → CI / stack → 合并与 Done。

哪些步骤不是每次都发生？

常见想象现有证据给出的答案
每次先写完整 Plan不是硬规则 仓库有 Plan 能力，但开发规则只强制非平凡变更维护 Agent Note；简单机械改动可直接做。
每次自动调用多个子 Agent无法确认 仓库支持 subagent，review guide 也提到 delegated fix，但没有证据表明所有任务都并行委派。
每次本地跑完整测试套件明确不是 规则要求选择最窄有效检查，CI 负责全量覆盖率和平台矩阵。
Codex 自己决定需求、开 PR 并合并无法确认 仓库能证明这些控制面存在，不能证明每一步由 Codex 自动执行。
一次提示后连续工作到完成更像多轮循环 真实分支包含实现、补测试、重构、修配置、文档调整、同步主线与评审修复。

从证据拼出的 Codex 生产工作流

下面不是仓库某一页逐字写出的“八步法”，而是多份官方材料和 Git 轨迹共同支持的重建。

1. 隔离任务为任务建立独立 branch/worktree；Git 历史中可见大量 codex/*、agent/* 与 worktree/* 分支合并记录。
2. 先装载规则让 Agent 读根 AGENTS.md、架构图和目标子树规则，先判断行为应该落在哪个扩展点。
3. 明确变更范围核对真实 PR base，再用 change-scope --base 汇总 committed、staged、unstaged、untracked 四层差异。
4. 把决定写下来非平凡改动同一 PR 必须新增或更新 Agent Note；提案写问题、方案、替代方案、验收与风险。
5. 代码、文档、证据同行实现不单独漂移；公共行为、JSDoc、README、双语材料、快照或真实入口测试按受影响表面一起改。
6. 运行最窄有效验证不是机械跑全仓：包行为跑定向测试，模型/UI 输出跑 snapshot，发布面跑 build/hygiene，真实 provider 跑 e2e。
7. PR 评审与修订评审追踪接口两侧、生命周期、并发、取消、模型所见文本、真实入口、负例和 Agent Note 是否与实现一致。
8. CI / stack / 合并本地 hooks 保持轻量，CI 负责完整矩阵；依赖 PR 使用官方 stack，变基后重新核验检查与评审状态。

最重要的设计：把“思考”变成长期资产

官方规则

Agent Note 不是聊天总结，而是可维护的决策对象

它按生命周期进入 proposed/、implemented/ 或 rejected/。提案必须写 Problem、Proposal、Alternatives considered、Acceptance criteria 与 Risks；实现后要改写为当前事实和 Consequences。来源：Agent Notes README。

工作流含义

人不必保存每句 prompt，但必须保存决策为何成立

会话可以丢；可复用的约束、被否决的方案、验收条件、风险和验证方式必须进入仓库。下一次 Codex 读取的不是上一轮聊天，而是已经压缩过的工程记忆。

官方规则

测试选择也不是固定流水线，而是按 diff 做语义判断

pre-push skill 要求先确认 base 和完整变更范围，再选最窄但有效的证据；本地 hooks 只做廉价高置信检查，完整覆盖与平台矩阵交给 CI。

你可以直接复用的 Codex 工作法

这是根据该仓库提炼的轻量版本，保留最关键的控制点，不要求照搬它的双语文档和复杂 CI。

  1. 一个任务一个 worktree / branch。分支名表达任务，不让两个 Agent 共写一个脏工作区。
  2. 先写仓库级 AGENTS.md。只放长期约束：结构、测试命令、禁止事项、交付定义。
  3. 让 Codex 先探索再改。要求它读规则、架构、目标模块和现有测试，先报告修改面与风险。
  4. 非平凡任务先产出短设计记录。至少含问题、方案、替代方案、验收标准和风险；确认后实现。
  5. 每轮只推进一个可验证增量。代码、对应测试和必要文档一起完成，失败证据直接进入下一轮。
  6. 让另一轮/另一 Agent review。重点查接口两侧、并发/清理、错误路径、模型可见文本与测试是否真会失败。
  7. 合并前压缩上下文。把长期有效信息留进文档与测试；删掉“上一轮我们如何争论”的会话残留。
先不要修改代码。请依次： 1. 阅读 AGENTS.md、架构文档、目标模块 README 与相邻测试； 2. 确认当前分支、真实 base、脏文件和完整变更范围； 3. 用“问题 / 方案 / 替代方案 / 验收 / 风险”写一份短计划； 4. 指出最小可验证实现切片，以及会运行的定向检查； 5. 等计划自洽后再实现。实现完成后，自审 diff，并报告证据与仍未验证的部分。
这套方法的核心不是“写一个更长 prompt”。它是把 Codex 放进一个有仓库规则、隔离工作区、持久决策、真实反馈和独立评审的循环。

能还原从任务到合并的工作流骨架可以规则文件定义阶段，Git 历史展示真实迭代顺序。
能还原某次 Codex 的完整逐轮工作过程不可以缺少 transcript、PR threads、模型配置与人类干预记录。
