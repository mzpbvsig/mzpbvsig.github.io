实践补充

Concept Map · DeepSeek Harness

Agent Note 和 Task / Sprint 很像吗？

外形有一点像，职责完全不同。Task 管执行，Sprint 管排期，Agent Note 管决策。在 DeepSeek Harness 的公开流程中，Task 和 Agent Note 都是正式对象；Sprint 并不是公开流程里的一等对象。

核验日期：2026-08-14 · 依据：Agent Notes 规范、文档分类规则、Issue/Task 模板、PR 模板和 Issue 生命周期实现。

最短答案 Agent Note 更像 ADR / Design Decision Record，不像任务清单。

它在实施前可能包含 Proposal、Acceptance criteria 和 Risks，所以乍看像 Task；但实施完成后必须删除计划与验收清单，改写为“已经交付的决定、替代方案、后果和验证依据”。

四个对象分别回答什么问题？

Task / Issue做什么？
谁负责、优先级、交付物、验收条件、测试证据、当前进度。
Sprint这段时间做哪些任务？
一个时间盒或批次容器。DeepSeek Harness 的公开流程没有把它建模为正式对象。
Agent Note为什么这样设计？
问题、选中的方案、落选方案、代价、收益、验证和重新讨论的边界。
Pull Request这次具体合入什么？
代码、测试、文档和 Agent Note 在同一可评审变更里汇合。

他有没有“全局记录”？有，但拆成三本账

它没有用一份万能文档同时管理需求、进度、代码和设计理由。不同事实进入不同的长期记录。

没有中央 Agent Note INDEX

这是刻意设计，不是遗漏

仓库曾明确决定不保留统一的 Agent Note 索引：每新增、移动或重命名一个 Note 都会改同一个索引文件，导致无关分支频繁冲突。目录路径已经编码 lifecycle、class 和日期，文件 H1 编码主题，所以他们选择浏览目录或全仓搜索。

官方逐字“The lifecycle/class filesystem tree is the Agent Note inventory.”生命周期/类别目录树本身，就是 Agent Note 的全局清单。— Keep Agent Notes discoverable without a generated index
重要边界：公开流程没有一张“Task ↔ Agent Note”中央映射表。关联由同一个 PR 承载：每个非平凡变更必须在该 PR 中新增或更新至少一个拥有该决定的 Agent Note。简单任务不写；已有 Note 能承载时只更新，不重复新建。

“从 Issue、PR、Note 三处拼接”具体是什么意思？

假设任务是“限制每个会话最多运行 4 个后台任务”。你打开其中任何一个对象，都只能看到全过程的一部分。

打开哪里通常能回答单靠它回答不了
Issue / Task
任务模板		为什么提出任务、交付物是什么、怎样验收、目前是 In progress 还是 Done。为什么最后采用“每个 session 单独计数”，而没有采用全局计数器。
Agent Note
Note 规范		设计问题、选中方案、落选方案、代价、收益、验证边界，以及决定是 proposed 还是 implemented。这个任务现在做到哪一步、对应哪个具体 PR、谁在处理 review——除非作者另外留下链接。

合并理解

用 Issue 还原“要做什么”，用 Note 还原“为什么这样做”，用 PR 还原“实际上怎么交付”。

官方逐字“Every non-trivial repository change must add or update at least one owning Agent Note in the same PR.”每个非平凡仓库变更，都必须在同一个 PR 中新增或更新至少一个负责该决定的 Agent Note。— Require an Agent Note for every non-trivial change
“拼接”的本质：不是复制文字，而是跨对象恢复关系。它甚至不一定是一对一：一个 Issue 可能拆成多个 PR，一个 PR 可能更新多个 Note，一个 implemented Note 又可能被未来多个 Task 继续复用。因此它没有你设想的那种“一条 Task 记录天然包含全部过程”。

一个任务过来，记录下来到底有什么用？

如果只保留 Task / 代码Agent Note 额外保存什么后续价值
Task 说“限制后台任务数量”为什么限制属于每个 session，而不是全局计数器下一次修改不会误把不同会话耦合起来
代码显示最后采用了方案 A方案 B、C 为什么落选，以及放弃了什么能力未来 Agent 不会重新提出已被验证有问题的方案
测试证明今天的行为能通过哪些验证是这个决定的长期约束，哪些覆盖仍缺失重构时知道哪些信号必须保持、哪些风险仍存在
PR 显示发生过若干轮修改最终成立的设计理由，而不是会话和 review 的过程噪声新的人或 Codex 无需读取完整历史即可恢复关键上下文
Task 完成后关闭决定继续处于 implemented，并随实际代码的路径、名称和默认值更新跨后续 Task、PR 和人员变动继续充当工程记忆
真正的复用场景

几个月后，新任务要求把 session limit 改成 tenant-wide limit

新的 Codex 不必从零猜测。它先搜索现有 Note，看见当初为何拒绝全局限制、所有权边界在哪里、哪些测试锁定当前行为；然后决定是更新现有 Note，还是新建一个 Note 正式推翻旧决定并交叉链接。记录的价值发生在下一个任务，不是当前任务里。

官方逐字“Code and tests show what changed, but they cannot consistently preserve why an approach won.”代码和测试能显示改了什么，却不能稳定保存为什么这个方案胜出。— Require an Agent Note for every non-trivial change

它真正的优点是什么？

这些优点只有在“大仓库、并行分支、多 Agent、设计决定经常被重新讨论”的环境里才明显。

减少共享文件冲突每个决定是独立文件。多个 Agent 新增不同 Note 时不会共同改一个中央索引，适合大量 worktree 和并行 PR。
保存负面知识不只记录采用了什么，还强制记录替代方案为何落选。下一轮 Agent 不必重新踩一遍已经分析过的坑。
与代码一起评审非平凡变更要求 Note 与实现处于同一个 PR；设计理由、代码、测试和文档在同一 diff 中接受审查。
不为简单任务制造文档机械和局部编辑豁免；已有 Note 能承载时只更新，不强制“一任务一文档”。
最核心收益

它让 Agent 获得“经过压缩的架构记忆”

下一次 Codex 不需要加载旧会话、完整 PR discussion 和几百个 commit 才理解设计。它读当前代码、当前 Note 和锁定行为的测试，就能恢复高价值上下文。

证据锚点：不提交中央索引以避免 merge hotspot；非平凡变更随同一 PR 记录决定，机械/局部修改豁免。上面的“压缩架构记忆”是根据这两条规则作出的实践性归纳，不是仓库逐字表述。

为什么它可能不符合你的思路？

因为它把“任务协调”和“决策记忆”彻底分开，而你关注的可能是任务作为第一等实体的完整生命周期。

你的可能诉求DeepSeek 当前做法产生的落差
一个任务有唯一入口和完整记录Issue 记录任务；Note 记录决定；PR 记录交付，分散在三个系统需要跨对象拼接全过程
随时看到做到哪一步Agent Note 只有决策生命周期，不记录执行进度Note 无法回答当前 blocker、下一步和完成百分比
任务、子任务、计划与决策一一可追踪公开流程没有强制的 Task ↔ Agent Note 中央映射依赖 PR、链接和搜索恢复关系
从一个页面进入全部上下文刻意拒绝 committed INDEX，要求浏览目录或搜索减少 Git 冲突，却增加人的发现成本
让 Agent 自动接续未完成工作Task 状态存在，但 Agent Note 不保存 checkpoint、下一动作和运行上下文不能只靠 Note 恢复执行现场
所以你的不适感很合理：Agent Note 是优秀的“决策记忆层”，但不是完整的“任务操作系统”。如果把它当成 Task/Sprint 的替代品，体验一定会割裂。

更符合你思路的混合方案

不要删除 Agent Note，而是把它降为 Task 下挂的“决策对象”；Task 才是用户和 Agent 的主入口。

全局主对象

Task Record

ID / goal / owner / status / priority / definition of done / current checkpoint / next action / blockers

→
执行结构

Plan / Phase / Subtask

记录如何拆解、依赖顺序、当前做到哪一步；这是 Agent 恢复工作时首先读取的状态。

→
按需附加

Agent Note

只有出现跨任务仍有价值的设计决定时创建，写 Related-Task: T-042，Task 反向链接 Note。

→
交付证据

PR / Tests / Docs

Task 记录关联 PR、检查结果、产物和最终总结；合并后状态进入 Done。

全局视图不必写成一个容易冲突的 committed INDEX

可以从 GitHub Issues、数据库或每个 Task 文件的 frontmatter 动态生成 dashboard。这样既有全局入口，也不会让所有并行 Agent 修改同一索引文件。

推荐规则
  • 每个任务必有 Task Record；Agent Note 不必有。
  • Task 保存执行状态；Note 只保存跨任务有价值的决定。
  • Task 与 Note 必须双向链接，避免依赖搜索猜关系。
  • Agent 每轮结束更新 checkpoint、next action 和验证结果。
  • Task 完成时写一段最终摘要；Note 继续跨任务存活。
一句话：DeepSeek 是“分布式决策记录优先”；更符合你描述的方案是“全局 Task 优先，Agent Note 按需挂载”。

为什么 proposed Agent Note 看起来很像 Task？

proposed 阶段

它确实包含未来工作信息

规范要求 proposed Note 写 Problem、Proposal、Alternatives considered、Acceptance criteria 和 Risks。实现者可以据此开工，所以它同时承担“设计提案”和“实现边界”的作用。

implemented 阶段

一旦交付，它必须停止像 Task

Note 移入 implemented/ 时，要把 Proposal 改写成现在时的 Decision，把验收和风险折入 Consequences 或 Verification，并删除迁移计划、未来时规格和 acceptance-task checklist。

官方逐字“Active decision records: the why, what-was-given-up, and required verification.”Agent Note 是活跃的决策记录：保留为什么、放弃了什么，以及必需的验证。— DeepSeek Harness documentation rules
判断窍门：如果一段内容在任务完成后就失去价值，它更可能属于 Task；如果五个月后有人准备推翻设计时仍需要它，它更可能属于 Agent Note。

它们在一次真实任务里怎么组合？

1 · Task

提出工作

“限制每个会话的后台任务数；超限要拒绝；补测试。”

→
2 · Agent Note

决定机制

为什么限制由 session owner 负责、默认值如何配置、为何不采用全局计数器、验证哪些生命周期。

→
3 · PR

交付实现

代码、单测、快照、README 和 Agent Note 一起进入 review。

  • 简单 Task 可以没有 Agent Note：例如纯机械、更正局部文字且不改变行为或约定。
  • 非平凡 Task 至少触及一个 Agent Note：新建，或更新已经拥有这个决定的 Note。
  • 一个 Task 可能涉及多个 Agent Note：例如同时改变架构、测试策略和发布流程。
  • 一个 Agent Note 也可能跨多个 Task/PR 演进：proposed 可以部分实现，后续变更继续更新，直到决定真正交付并改写为 implemented。

Sprint 在这个仓库里处于什么位置？

证据边界

公开流程没有 Sprint 一等对象

在 AGENTS.md、.agents/、docs/ 与 .github/ 的流程文档中检索不到 sprint。公开的项目控制面是 Issue Type、Priority、Owner、Status、PR 和 stack。因此，不能声称 DeepSeek 团队内部完全不用 Sprint；只能确认公开仓库没有靠 Sprint 驱动这套 AI Coding 流程。

如果你自己的团队使用 Sprint

可以把 Sprint 放在最外层：Sprint 包含多个 Task；Task 通过 PR 交付；遇到非平凡设计决定时，PR 同时创建或更新 Agent Note。Agent Note 不属于某个 Sprint 的临时资产，它应跨 Sprint 存活。

别把 Agent Note 写成这三种东西

错误写法为什么错应该放哪
“Task 1 改接口，Task 2 补测试，Task 3 更新文档”这是执行清单，完成后会过期。Task、Issue、PR checklist 或实施计划
“本 Sprint 要完成 A/B/C”这是时间盒与容量管理，不是设计理由。Sprint board
“我们先试了五次，reviewer 在第三轮要求……”这是会话/评审过程叙事，不是当前可验证事实。PR thread、commit history；只把仍有效的理由提炼进 Note
“采用 per-session limit，因为所有权属于 session；否决 global limit，因为不同会话会相互干扰”这是长期有效的决定与替代方案。Agent Note
