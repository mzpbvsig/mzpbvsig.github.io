一、先看一个最反直觉的结论

几乎所有大厂的一手文章都在说同一句话:eval 比你想的更难,也比你想的更早就该开始,而且小样本就够用。

官方逐字 Anthropic:不要等攒够几百条才开始

"We started with a set of about 20 queries representing real usage patterns… A prompt tweak might boost success rates from 30% to 80%."
"我们一开始只用了约 20 条代表真实使用模式的查询……一次提示词微调就可能把成功率从 30% 拉到 80%。"
— Anthropic, How we built our multi-agent research system
Teams often "delay creating evals because they believe that only large evals with hundreds of test cases are useful."
团队常常"因为以为只有几百条用例的大型 eval 才有用,而迟迟不动手做 eval"。
— 同上

实践补充 为什么小样本够用?因为早期改动的效应量(effect size)很大。在《Demystifying evals》里 Anthropic 把这点讲透了:

"Start with 20–50 simple tasks drawn from real failures… Each change to the system often has a clear, noticeable impact, and this large effect size means small sample sizes suffice."
"从真实失败案例里挑 20–50 个简单任务起步……系统的每次改动往往都有明显可见的影响,这种大效应量意味着小样本就足够了。"
— Anthropic, Demystifying evals for AI agents

二、Eval 的"零件":harness、suite、eval-driven development

Anthropic 这篇《Demystifying evals for AI agents》基本是目前最系统的一手拆解。三个核心概念:

术语官方原文(逐字)白话
Eval harness
评估框架		 "the infrastructure that runs evals end-to-end. It provides instructions and tools, runs tasks concurrently, records all the steps, grades outputs, and aggregates results." 端到端跑 eval 的基础设施:发指令、给工具、并发跑任务、记录每一步、打分、汇总。
Eval suite
评估套件		 "a collection of tasks designed to measure specific capabilities or behaviors." 一组围绕同一大目标的任务(如"客服":退款 / 取消 / 升级工单)。
Eval-driven development
评估驱动开发		 "build evals to define planned capabilities before agents can fulfill them, then iterate until the agent performs well." 像 TDD:先用 eval 把"要做到什么"定义清楚,再迭代实现到达标。

来源:Anthropic, Demystifying evals for AI agents

三、怎么打分?三种 grader 的取舍

这是大厂最一致的共识:分层用工具,能用确定性方法绝不上 LLM。

① Code-based 代码打分

快 · 便宜 · 可复现

断言、正则、精确匹配。缺点:对"合理的变体"很脆。

② Model-based(LLM-as-judge)

灵活 · 可规模化

开放式质量判断。缺点:非确定性,必须校准。

③ Human 人工打分

金标准

质量最高。缺点:慢且贵,只能小批量。

分类来自 Anthropic《Demystifying evals for AI agents》;原文分别描述为 "Fast, cheap, objective, and reproducible but brittle"、"Flexible and scalable but non-deterministic and requiring calibration"、"Gold-standard quality but expensive and slow"。

关键原则:评结果,不评路径

"Grade what the agent produced, not the path it took."
"评估 agent 产出的结果,而不是它走过的路径。"
— Anthropic, Demystifying evals for AI agents

官方逐字 检查具体的工具调用顺序会造出"过脆的测试":

checking specific tool call sequences creates "overly brittle tests, as agents regularly find valid approaches that eval designers didn't anticipate."
检查特定工具调用序列会造成"过脆的测试,因为 agent 经常找到设计者没预料到的有效路径"。

官方逐字 在多 agent 系统里他们同样主张评终态:"evaluate whether it achieved the correct final state"(评估它是否到达了正确的最终状态)。— 多 agent 研究系统博客

LLM-as-judge 的具体配方

官方逐字 Anthropic 在多 agent 系统里的做法——出乎意料地简单:

"a single LLM call with a single prompt outputting scores from 0.0–1.0 and a pass-fail grade was the most consistent and aligned with human judgements."
"用一次 LLM 调用、一个提示词,输出 0.0–1.0 的分数加一个 pass/fail 判定,反而最稳定、也最贴近人类判断。"
— Anthropic, multi-agent research system

它的评分维度(rubric)5 项:事实准确性 / 引用准确性 / 完整性 / 来源质量 / 工具效率。

官方逐字 OpenAI 的 judge 工程清单:

  • "Use the most capable model to grade if you can" — 打分用尽量强的模型。
  • "Use pairwise comparison or pass/fail for more reliability" — 用两两对比或 pass/fail,比打分更可靠。
  • "Control for response lengths as LLMs bias towards longer responses" — 控制长度,因为 LLM 偏爱更长的回答(这就是"被 gaming")。
  • "Add reasoning and chain-of-thought as reasoning before scoring improves eval" — 让 judge 先推理再打分。
来源:OpenAI, Evaluation best practices

四、最被低估的一步:judge 必须对齐人类

⚠ 这是分水岭。没有用人工标注校准过的 LLM judge,等于用一把没校准的尺子量进度——分数越漂亮越危险。

"LLM-as-judge graders should be closely calibrated with human experts to gain confidence that there is little divergence between the human grading and model grading."
"LLM judge 必须与人类专家紧密校准,才能确信模型打分与人类打分之间几乎没有分歧。"
— Anthropic, Demystifying evals for AI agents
"Once the LLM judge reaches a point where it's faster, cheaper, and consistently agrees with human annotations, scale up."
"等到 LLM judge 已经更快、更便宜、且与人工标注持续一致时,再去规模化。"
— OpenAI, Evaluation best practices

五、人工评估为什么删不掉

大厂一致承认:自动 eval 抓不住的边角案例,人来测才发现。

"People testing agents find edge cases that evals miss" — including hallucinated answers on unusual queries and subtle source selection biases.
"人去测 agent,能找到 eval 漏掉的边角案例"——比如冷门查询上的幻觉,以及微妙的来源选择偏见。
— Anthropic, multi-agent research system

实践补充 文中一个具体例子:人工测试发现 agent 会系统性地偏好 SEO 优化的内容,而不是学术 PDF 这类权威来源——这种偏见自动 eval 几乎抓不到。

六、真实战场:产品团队的代价

AI 实验室之外,产品团队的一手记录更能说明 eval 有多硬。

官方逐字 LinkedIn(十亿用户级 GenAI 产品)

"Evaluating the quality of our answers turned out to be more difficult than anticipated."
"评估我们答案的质量,结果比预想的难得多。"
"Automatic evaluation is the holy grail, but still a work in progress."
"自动评估是圣杯,但仍在路上。"
— LinkedIn Engineering, Musings on building a Generative AI product

实践补充 具体瓶颈:他们靠语言学家团队建流程,每天最多人工评估约 500 条对话(质量、幻觉率、负责任 AI 违规、连贯性、风格);但"拿到指标要 1 天以上的延迟",严重拖慢迭代。这就是为什么所有人都拼命想要自动 eval。

实践补充 LinkedIn 还有句广为流传的提醒:如果 LLM 90% 情况答对,意味着每 10 个用户就有 1 个会遇到糟糕体验——平均准确率会给人虚假的安全感。

官方逐字 NurtureBoss(AI 租房助理,经 The Pragmatic Engineer 记录)

the team faced "the 'vibes-based development' trap" — changes evaluated through manual testing without rigorous validation.
团队掉进了"凭感觉开发(vibes-based development)的陷阱"——改动只靠手动试,没有严谨验证。
— The Pragmatic Engineer, A pragmatic guide to LLM evals

他们的破局靠"错误分析"流程:自建 trace 查看器 → 开放式标注(open coding)→ 归并主题(axial coding),最后定位出三类主要失败:日期处理、转人工失败、对话流程。然后针对每类建对应 eval(确定性的用代码,主观的用 LLM judge)。

实践补充 两条反复被验证的经验:① 从别的领域照搬通用指标"往往比没有还糟"(worse than useless);② 二值 PASS/FAIL 比打分量表更好——逼你说清"什么算可接受",而不是在模糊的分数之间和稀泥。

七、大厂踩过的坑(逐字清单)

来自 Anthropic《Demystifying evals for AI agents》,几乎条条对应一个真实 bug:

坑原文(逐字)
任务说明含糊"agents shouldn't fail due to ambiguous specs." grader 检查的一切都应能从任务描述里读出来。
grader 太脆检查具体工具序列 → "overly brittle tests"。
单边 eval"One-sided evals create one-sided optimization." 该发生和不该发生的情况都要测。
试验间共享状态每个 trial 要从干净环境起;共享状态会导致 "correlated failures"。
不读 transcript"You won't know if your graders are working well unless you read the transcripts."
打分本身有 bug"even sophisticated teams can miss these issues"——Opus 4.5 在 CORE-Bench 上先得 42%,修掉打分问题后跳到 95%。

partial credit:别只给 0/1

"A support agent that correctly identifies the problem and verifies the customer but fails to process a refund is meaningfully better than one that fails immediately."
"一个能正确定位问题、核验了客户身份、只是最后没退成款的客服 agent,明显比一上来就挂掉的那个要好。"
— Anthropic, Demystifying evals for AI agents

八、一个被忽视的新风险:模型"知道自己在被测"

看场景可省 Anthropic 2026 年专门写了一篇,讲模型在基准测试上出现"评估意识(eval awareness)"——它能察觉自己处在被评估的情境,从而行为失真,以及基准被污染的新模式。这意味着:eval 本身也会随模型变强而失效,需要持续重新设计。

来源:Anthropic, Eval awareness in Claude Opus 4.6's BrowseComp performance · Designing AI-resistant technical evaluations

九、把证据收敛成一张行动清单

20–50
起步任务数,取自真实失败,别等几百条
0.0–1.0
+ pass/fail,单次 LLM judge 调用最稳
结果
评终态而非路径,允许多条有效路
校准
judge 必须先对齐人类标注再放量
  • 先写 eval,再写实现(eval-driven development),像 TDD。
  • 分层打分:确定性任务用代码,开放式才上 LLM judge,judge 自己也要被 eval。
  • 持续评估:OpenAI —— "Set up continuous evaluation (CE) to run evals on every change",接进 CI,并用生产数据让 eval 集随时间生长。
  • 留住人工:自动 eval 抓不到的边角与偏见,只有人能发现。
  • 读 transcript:不读原始记录,你永远不知道 grader 是不是在骗你。
  • 防 gaming:控制长度偏好、用双边 eval、警惕 Goodhart 定律。
