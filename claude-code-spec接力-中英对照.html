① 访谈挖需求 → 写出 spec

官方逐字Claude Code 原生：让它面试你，再写 SPEC.md官方 BP ↗
English（直接复制用）
I want to build [brief description]. Interview me in detail using the AskUserQuestion tool.

Ask about technical implementation, UI/UX, edge cases, concerns, and tradeoffs. Don't ask obvious questions, dig into the hard parts I might not have considered.

Keep interviewing until we've covered everything, then write a complete spec to SPEC.md.
中文对照
我想做【简要描述】。请用 AskUserQuestion 工具详细地面试我。 就技术实现、UI/UX、边界情况、顾虑和取舍来提问。别问显而易见的问题，深挖我可能没考虑到的难点。 一直问下去，直到我们把所有内容都覆盖了；然后把一份完整的 spec 写到 SPEC.md。

② 把讨论编译成可交付的规格文件

实践者逐字收口：编译成"开发者可直接开工"的规格Harper Reed ↗
English（直接复制用）
Now that we've wrapped up the brainstorming process, can you compile our findings into a comprehensive, developer-ready specification? Include all relevant requirements, architecture choices, data handling details, error handling strategies, and a testing plan so a developer can immediately begin implementation.
中文对照
既然我们已经完成了头脑风暴，你能把我们的结论汇编成一份全面、可供开发者直接上手的规格吗？包含所有相关需求、架构选择、数据处理细节、错误处理策略，以及一份测试计划，好让开发者能立刻开始实现。
实践者逐字生成"实现蓝图"：拆小步、强制 TDDHarper Reed ↗
English（直接复制用）
Draft a detailed, step-by-step blueprint for building this project. Then, once you have a solid plan, break it down into small, iterative chunks that build on each other... Prioritize best practices, incremental progress, and early testing, ensuring no big jumps in complexity at any stage...
中文对照
为构建这个项目起草一份详细的、分步骤的蓝图。然后，等你有了扎实的计划，把它拆成层层递进的小块……优先考虑最佳实践、增量推进和尽早测试，确保任何阶段都不出现复杂度的大跳跃……

③ spec 必须"自包含"才接得住（官方原则 · 对照）

name the files and interfaces involved
点名涉及的文件与接口
state what is out of scope
写明哪些不在范围内（out of scope）
end with an end-to-end verification step that proves the feature works
结尾给一个端到端验证步骤，证明功能确实能用
Time spent making the spec precise pays off more than time spent watching the implementation.
把 spec 写精确所花的时间，比盯着实现过程更值。
官方 Best practices ↗

④ 换干净会话执行（接力动作 · 对照）

/clear (or open a new session / new window)
/clear（或开新会话 / 新窗口），让上下文干净
Implement the feature described in SPEC.md. Follow tasks.md in order, update its status as you go, and run the tests after each step.
实现 SPEC.md 里描述的功能。按 tasks.md 的顺序来，边做边更新其状态，每步之后都跑测试。
为什么要换新会话：同一会话里 Claude 带着写 spec 时的隐含假设，会停止逐字读 spec；新会话强迫它像新工程师一样从头逐字读。〔buildthisnow〕

spec 文件三种形态（对照速查）

SPEC.md (single, self-contained)
官方：单文件、自包含
requirements / design / tasks
最小三段：需求（用户故事+验收）/ 设计（数据模型·API·改哪些文件）/ 任务（有序·列依赖）
spec.md / prompt_plan.md / todo.md
Harper：规格 / 可粘的实现 prompt 集 / 勾选清单
注意plan mode ≠ spec 接力
  • plan mode（Shift+Tab）把计划写进 Claude 自己的 plans 文件夹，退出时从磁盘读回再执行——但它是同一会话 approve→执行，不是干净上下文接力，且 plan 文件藏在文件夹里不好手动审改。〔Armin Ronacher〕
  • 所以大功能想真正"接力"，用形态 A（自己控的 SPEC.md），别只依赖 plan mode。
