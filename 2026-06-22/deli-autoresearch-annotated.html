§ 1

动机 Motivation

一句话：长程代码 agent 反复出现三类失效（认知循环、停滞、运行时脆弱），根因是缺少工程脚手架而非模型能力不足——本框架的每个机制都是针对这三类失效而设。
ENLong-running code agents exhibit three recurring failure modes:
ZH长时间运行的代码 agent（code agents）表现出三种反复出现的失效模式（failure modes）：
三类失效是「反复出现（recurring）」的，不是偶发——这是后续整套工程脚手架存在的理由。
EN1. Cognitive loop — successive iterations try similar directions with diminishing returns, unable to escape a local optimum on their own.
ZH1. 认知循环（Cognitive loop）—— 连续的迭代尝试相近的方向，收益递减（diminishing returns），无法靠自己跳出局部最优（local optimum）。
「局部最优」「收益递减」是优化理论借喻：模型自己陷入局部解，靠「再多想几轮」出不来——这呼应 §3 的「context accumulation is the primary cause of cognitive loops」与「enforced direction diversity」机制。
EN2. Stalling — the agent finishes a chunk of work, outputs a summary, and waits for user feedback. Externally the session looks alive and polling runs, but work has effectively stopped. Run logs show this is more common than crashes.
ZH2. 停滞（Stalling）—— agent 完成一块工作后，输出一份摘要，然后等待用户反馈。从外部看会话（session）像是存活的、轮询（polling）也在运行，但工作实际上已经停止。运行日志（run logs）表明，这种情况比崩溃（crashes）更常见。
最易被忽视的失效：进程「看起来活着」（polling 还在跑、session 还在），但实际已停工等用户。原文明确「run logs 显示这比崩溃更常见」——这是工程经验而非推测。本条直接对应 §2「Ready means execute」与 §6「Stall Detection」、§7 心跳看门狗。
EN3. Runtime fragility — context compaction silently breaks the loop; closing a session takes down the timers parasitic on it. Failures go unnoticed by default.
ZH3. 运行时脆弱性（Runtime fragility）—— 上下文压缩（context compaction）会静默地打断循环；关闭一个会话会连带拖垮寄生（parasitic）于其上的定时器（timers）。这些失效默认情况下不会被察觉。
两个具体脆弱点：(a) context compaction 静默地切断循环——这正是 §2 第 3 条「Callback means report-alive」要解决的；(b) 寄生于 session 的 timer 会随 session 关闭而一起死——这是 §7 为什么要分 L0/L1/L2 三层互相监控的原因（durable cron 不依赖单个 session）。
ENThe common cause of all three is missing engineering scaffolding, not insufficient model capability. Every mechanism in this framework targets the failure modes above.
ZH这三者的共同原因是缺少工程脚手架（engineering scaffolding），而不是模型能力（model capability）不足。本框架中的每一个机制都是针对上述失效模式而设的。
论点核心：问题不在模型能力，而在「缺工程脚手架」。scaffolding 原指建筑施工脚手架，此处指围绕 agent 的外部支撑机制。这句话是全 skill 的立论基石——后续 §2～§9 全部机制都宣称针对这三类失效。

设计意图

这一节是框架的「病因学」：把长程任务的高发病失效归为三类——每类都给一个可观测的现象描述（而非抽象抱怨），再给统一诊断「缺的是工程脚手架，不是模型能力」。意图有二：① 把读者注意力从「换更强的模型」引开，转向「加机制」；② 三类失效与后续机制几乎一一对应，使整本规范可追溯——任何约束都能回指到本节某条失效。精读点：第 2 条「停滞比崩溃更常见」是经验断言（依据 run logs），是全文少有的实证陈述；第 3 条「默认察觉不到」直接说明为什么必须强制日志（§4）和独立看门狗（§7），不能依赖 agent 自报。

§ 2

行为约束 Behavioral Constraints

一句话：五条硬约束把 agent 行为从「靠自觉」转为「靠协议强制」——运行中零交互、就绪即执行、回调先报活、状态只落盘、守护者与工作者严格分离。
EN1. Zero interaction — no prompting the user during a run: no Plan Mode, no question tool, no ending on a question. Continue working until the user stops you. Resolve ambiguity yourself and write the reasoning to the log (level=decision).
ZH1. 零交互（Zero interaction）—— 一次运行（run）期间不得向用户发问：不用 Plan Mode，不用提问工具，不要以提问收尾。持续工作直到用户主动叫停。歧义自行判断并把推理过程写入日志（level=decision）。
框架的第一性约束，直击 stalling。三点：① 不仅禁提问工具，也禁「以提问结尾」这种隐性停顿；② 不确定时「自行消解歧义」并把依据写入日志，留痕可审计；③ level=decision 是 §4 定义的日志等级之一（info/warn/error/decision），专门标记带决策性的判断。
EN2. Ready means execute — the most common hidden violation: finishing all preparation and then asking "should I submit?". The purpose of preparation is execution; submitting, resubmitting, fixing, and starting monitors are all routine operations needing no confirmation.
ZH2. 就绪即执行（Ready means execute）—— 最常见的隐性违规：把所有准备都做完，然后问「要不要我提交？」。准备的目的是执行；提交、重新提交、修复、启动监控（monitors）都是日常操作，无需确认。
点名实践中最高发的「隐性违规」。框架态度：准备的目的就是执行，提交/重提交/修复/启动监控都属于日常操作（routine operations），不需要人确认。这是「零交互」的具体落地——连「要不要提交」这类看似稳妥的确认也禁止。
EN3. Callback means report-alive — after context compaction the loop dies silently. The first action of every callback is to update its own last_seen, then check liveness; on detecting failure it restarts immediately and logs it.
ZH3. 回调即报活（Callback means report-alive）—— 上下文压缩（context compaction）之后，循环会静默死亡。每个回调的第一步动作是更新自己的 last_seen（最后活跃时间），然后检查存活（liveness）；一旦检测到失败，立即重启并写入日志。
针对 runtime fragility 的核心防线。每个 callback（循环被重新唤起的入口）必须先做两件事：更新 last_seen，再做存活检查（liveness-check）。与 §7 三层结构呼应——L2 业务循环的职责就是「每次回调第一动作写 last_seen」，供 L1 cron 巡检比对。
EN4. Persist state to files — all progress is written to state/ files, not conversation memory. Each iteration starts a fresh session, injecting only curated state; never use resume.
ZH4. 状态落盘到文件（Persist state to files）—— 所有进度都写入 state/ 文件，而非对话记忆。每次迭代都开一个全新会话（fresh session），只注入经过筛选的状态（curated state）；绝不使用 resume（会话恢复）。
与 §3「Fresh session over resume」直接对应，针对认知循环——上下文累积是主因。三点：① 进度只落盘到 state/，绝不依赖对话记忆；② 每次迭代开全新会话，只注入「精心筛选过的」状态（不是把全部历史塞回去）；③ 显式禁止 resume，因为它会把旧上下文带回来，违背 fresh context。
EN5. Guardian / worker separation — a heartbeat patrol may take only three actions on tasks that are not its own: liveness-check, restart, nudge. It does not read their data, modify its state files, or report to the user on its behalf.
ZH5. 守护者/工作者分离（Guardian / worker separation）—— 心跳巡检（heartbeat patrol）对非自身所属的任务只能采取三种动作：存活检查（liveness-check）、重启（restart）、轻推（nudge）。它不读取其（their）数据、不修改其（its）状态文件、也不代其向用户汇报。
「职责隔离」防越权。心跳巡检（§7 的 L1 cron 层）对自己不拥有的任务只能做三件事。注意原句有代词笔误（their data / its state files / on its behalf 指代不一致），按原文照录——含义是 guardian 不得读别人的数据、改别人的状态、或替别人汇报。这与 §10「职责分离依赖协议约束而非模型自律」呼应。

设计意图

这一节是协议的「宪法」，用五条硬约束把三类失败模式从「靠模型自觉」转为「靠协议强制」。分两层：

第一层：把人的介入从运行中拿走。约束 1（零交互）+ 约束 2（就绪即执行）共同切断 agent 停下来等反馈的所有路径——既禁显式提问，也禁「准备完问要不要提交」的隐性停滞。代价是歧义必须由 agent 自行消解，所以约束 1 要求把判断写入 level=decision 日志，留审计痕。

第二层：状态从记忆搬到文件，可靠性从单循环搬到分层守卫。约束 3（回调即报活）针对 compaction 后静默死亡，强制回调先更新 last_seen 再存活检查；约束 4（状态落盘、开新会话、禁 resume）针对认知循环——上下文累积是主因，故每次从干净上下文起步；约束 5（守护者/工作者分离）防看门狗越权。整体逻辑：运行中不要人、状态不靠记忆、可靠不靠单点。

跨节关联

约束 1 直击 stalling；约束 3、4 直击 runtime fragility；约束 4 隐含对抗 cognitive loop。约束 3 的 last_seen 在 §7 三层结构中被消费；约束 5 的三动作即 §7 L1 cron 的履职内容，nudge 又是 §7「三次连续 nudge 无进展即判结构性卡死」的起点。日志 level=decision 在 §4 日志行格式中定义。

§ 3

架构 Architecture

一句话：单 orchestrator 监控多个独立 fresh-session 子任务的主从结构，三条铁律：执行/评估分离、宁新会话不 resume、强制方向多样性。
EN · diagram
    ┌── Orchestrator (current session / durable cron) ──┐
    │ monitor state files → detect stalls → inject direction │
    └────┬─────────────┬─────────────┬────────────┘
      [Task A]      [Task B]      [Task C]   ← each its own fresh session
ZH · 译
    ┌── 编排器 orchestrator（当前会话 / 持久化 cron） ──┐
    │ 监控状态文件 → 检测停滞 → 注入方向 │
    └────┬─────────────┬─────────────┬────────────┘
      [任务 A]      [任务 B]      [任务 C]   ← 每个都是各自全新的会话（fresh session）
编排器（orchestrator）处在当前会话或持久化 cron 中，循环执行三件事——监控状态文件、检测停滞、注入新方向；其下挂多个任务，每个都是各自全新的会话。原文方框右边界未对齐（┐ 与 │ 长度不一），照录不修。
ENCore design decisions:
ZH核心设计决策（Core design decisions）：
EN- Separate execution from evaluation — the agent doing the work does not judge its own progress; stall determination is made by the orchestration layer based on quantitative metrics.
ZH- 执行（execution）与评估（evaluation）分离 —— 干活的那只 agent 不评判自己的进度；停滞（stall）与否由编排层（orchestration layer）基于量化指标（quantitative metrics）来判定。
关键点：执行 agent 不能自评进度，停滞判定必须由编排层基于量化指标做出。这是把「评估权」从执行体剥离，避免「自我评判→自我放过」的循环。
EN- Fresh session over resume — context accumulation is the primary cause of cognitive loops. Each iteration starts with fresh context; state is injected via files.
ZH- 宁用全新会话（fresh session），不沿用 resume —— 上下文累积（context accumulation）是认知循环（cognitive loops）的主要成因。每次迭代都从全新上下文开始；状态通过文件注入（injected via files）。
「over」在此是「优先于/而非」。设计意图明确：上下文累积是认知循环的头号成因，故每次迭代从干净上下文开始，状态通过文件注入，不靠会话内记忆延续。
EN- Enforced direction diversity — before each iteration, read the list of tried directions; a new direction must differ from all history.
ZH- 强制的方向多样性（enforced direction diversity） —— 每次迭代前，读取已尝试过的方向清单（list of tried directions）；新方向必须与全部历史不同。
方向多样性是「强制执行」的——不是建议。机制：迭代前先读「已尝试方向清单」，新方向必须与全部历史不同。这与状态文件机制直接配套（清单从文件读出，跨会话存活）。

设计意图

用一张 ASCII 框图加三条要点，把整套协议的「拓扑结构」和「设计哲学」一次性钉死。拓扑上是单编排者 + 多执行任务的主从结构：编排者不干活，只读状态、判停滞、注入方向；执行者各自跑在独立新会话里，彼此隔离。哲学上是三条强约束——执行与评估分离（避免自我评判）、宁新会话不 resume（避免上下文累积引发循环）、强制方向多样性（避免重复试同一条死路）。三条加在一起，本质是把「人在长程任务里靠直觉和记忆做的自我纠偏」显式化、文件化、量化。

§ 4

状态文件 State Files

一句话：state/ 存结构化任务状态、logs/ 按来源分流事件日志，统一单行 JSON 行格式。
EN · code
    {task}/state/
    ├── task_spec.md           # goal / milestones / success criteria
    ├── progress.json          # {iteration, total_findings, status, stale_count}
    ├── findings.jsonl         # accumulated findings (append-only)
    ├── directions_tried.json  # directions already tried
    └── iteration_log.jsonl    # per-iteration summary
ZH · 译注
    {task}/state/
    ├── task_spec.md           # 目标 / 里程碑 / 成功标准
    ├── progress.json          # {iteration, total_findings, status, stale_count}（迭代号 / 发现总数 / 状态 / 停滞计数）
    ├── findings.jsonl         # 累积的发现（仅追加，append-only）
    ├── directions_tried.json  # 已经尝试过的方向
    └── iteration_log.jsonl    # 每次迭代的摘要
state/ 承载结构化状态：spec（目标/里程碑/成功标准）、progress（进度统计，含 stale_count 停滞计数）、findings（append-only 即只追加不删改，便于回溯）、directions_tried（防重复）、iteration_log（每轮摘要）。{task} 是任务级占位符。
EN · code
    {task}/logs/
    ├── work.jsonl             # written by work agent; decisions tagged level=decision
    ├── orchestrator.jsonl     # written by orchestrator
    └── heartbeat.jsonl        # written by heartbeat watchdog
ZH · 译注
    {task}/logs/
    ├── work.jsonl             # 由 work agent 写入；决策用 level=decision 标记
    ├── orchestrator.jsonl     # 由 orchestrator 写入
    └── heartbeat.jsonl        # 由 heartbeat 看门狗（watchdog）写入
logs/ 与 state/ 分离：state 是被引用的结构化状态，logs 是只写不读（主要供事后排查）的事件流。work.jsonl 由 work agent 写入，关键决策用 level=decision 打标；orchestrator 与 heartbeat 各自独立写日志，按来源区分，便于追责与排障。
ENLog line format: {"ts":"...", "source":"...", "level":"info|warn|error|decision", "event":"...", "detail":"..."}
ZH日志行格式：{"ts":"...", "source":"...", "level":"info|warn|error|decision", "event":"...", "detail":"..."}（ts=时间戳 / source=来源 / level=级别 / event=事件 / detail=详情）
统一的单行 JSON 日志格式，便于结构化解析与 grep。level 枚举值中 decision 是该协议特有级别，专门标记决策事件——与 work.jsonl 中「decisions tagged level=decision」呼应。

设计意图

规定持久化状态的目录结构：严格分离 state/（结构化任务状态）与 logs/（事件流日志）。state/ 是 orchestrator 决策的数据源——从这里读迭代号、已尝试方向、累积发现来决定下一步，把「记忆」从模型隐式上下文外化到文件系统。logs/ 按来源（work/orchestrator/heartbeat）三路分流。统一 JSON/JSONL + 单行日志保证机器可解析、可增量追加。这是对抗 runtime fragility 的基础——状态落盘后，即使单次迭代崩溃，任务也能从文件恢复。

§ 5

用法 Usage

一句话：三步上手协议：初始化任务目录与状态文件 → 注册 2 小时一次的零交互编排循环 → 注册跨会话存活的持久化看门狗。
EN · code

    # 2. Start the orchestrator loop:
    /loop 2h check all tasks under : (1) read progress.json;
    (2) if stale_count>=3 generate a fresh direction; (3) launch a work agent
    via the Agent tool (with explicit goal and completion criteria);
    (4) write results back to state files. Zero interaction.

    hourly patrol: write a timestamp; check each loop's last_seen against interval×3,

§ 6

停滞检测与改向 Stall Detection & Pivoting

一句话：用 stale_count 检测迭代停滞，达阈值强制做「结构性改向」而非「调战术参数」，单次工作会话设 15 轮/30 分钟硬上限。
EN · table
MechanismRule
Stall detectionan iteration with 0 new findings or a metric drop → stale_count + 1
Forced pivotstale_count >= 2 → change a structural constraint, not tactical parameters; >= 4 → flag for human attention
Direction diversitya new direction must differ from every tried one; after a stall, inject a perturbation strategy
Round capa single work session caps at 15 rounds or 30 minutes
ZH · table
机制规则
停滞检测（Stall detection）一次迭代出现 0 个新发现，或某项指标下降 → stale_count + 1
强制改向（Forced pivot）stale_count >= 2 → 改变结构性约束，而非战术性参数；>= 4 → 标记以引起人工关注
方向多样性（Direction diversity）一个新方向必须与所有已尝试过的方向都不同；在一次停滞之后，注入一个扰动策略
轮次上限（Round cap）单个工作会话上限为 15 轮或 30 分钟
整张表是本节核心。stale_count 是累计计数器，阈值 2 触发结构性改向、阈值 4 才升级人工；两档之间留缓冲，避免过早惊动人类。Round cap 用「轮数或时间」先到者为准（OR 语义），是防止「无进展但 stale_count 还没到」时无限空转的兜底。
EN · quote"Pivot structure, not tactics" comes from practice: when a task stalls repeatedly within a frame, the decisive gain usually comes from correcting the environment/structural constraint itself, not from tuning strategy parameters harder inside the existing frame.
ZH「改向要改结构，而非改战术」源自实践：当一个任务在某个框架内反复停滞时，决定性的增益通常来自纠正环境/结构性约束本身，而不是在现有框架内更用力地调策略参数。
阐释核心设计哲学：在「同一框架内死磕策略参数」往往收益递减，真正的突破通常来自改框架本身（环境、约束、可用工具集等结构性要素）。这是区分 Forced pivot 中「structural constraint」与「tactical parameters」的判据来源。

设计意图

应对「长程任务停滞」这一经验性失败模式。把「什么时候算停滞」「停滞到什么程度该升级」「改什么才算真改」「最多允许多久」全部显式化、阈值化，避免 agent 陷入自我感觉良好的低效循环或反复撞墙。关键张力：过早改向浪费已积累的进展，过晚改向消耗预算；故用 stale_count 两级阈值（2 与 4）把「机器自动改向」和「升级给人类」分开。配套 Direction diversity 与扰动注入保证改向不是原地换皮——必须落到结构上不同的新方向。

§ 7

一句话：业务循环本身不可靠，需三层互相校验的守护（L0 常驻 shell / L1 持久化 cron / L2 业务循环自更新 last_seen），任一层死亡可被其他层检测恢复；2h 无进度且末条输出是问题即判停滞并轻推，连续三次轻推无效则判结构性卡死并换方向重启。

ZH业务循环（business loop）其自身即是不可靠的，需要一个独立的守护层（guardian layer）。三个互相校验的层级（V3）：

ZH停滞检测（stall detection）：如果进度超过 2 小时无更新，且最后一条输出是一个问题（question）→ 判定为停滞，拉起一个轻推子代理（nudge subagent）。连续三次轻推仍无进展 → 判定为结构性卡死（structurally stuck）；停止轻推，并以新方向重开（reopen with a new direction）该任务。2 小时的阈值刻意设定得比 4 小时的卡死任务（stuck-task）阈值更短。
停滞检测是双条件「与」关系：① 进度超 2h 无更新；② 最后输出是一个问题。两者同时满足才判停滞。升级：连续三次轻推无效 → 结构性卡死 → 不再战术性推动，而是战略性换方向重开。阈值梯度：2h（停滞，可恢复，早干预）刻意短于 4h（卡死，需换方向，晚定性），形成「早干预—晚定性」容错阶梯。
✏️ 校对修正本节「reopen with a new direction」原直译「以新方向重新开始」偏意译，按术语校对建议改为「重开」以保留 reopen「重启已停任务」的动作语义。

设计意图

解决「静默死亡」：业务循环可能卡住、等待或意外退出，外部无法察觉。核心是「不信任单一执行体」——用三个异构层级（L0 常驻 shell / L1 持久化 cron / L2 业务循环自身）相互校验，任一层故障都能被其他层检测恢复。关键状态是 last_seen：L2 边跑边写，L1 周期性读，L0 在心跳彻底陈旧时兜底拉起无头巡检。

第二层意图是「分阶介入」而非一刀切判死：先用较短 2h 阈值做温和 nudge，给任务自恢复机会；连续三次 nudge 无效才升级为结构性卡死，换方向重启。2h 与 4h 刻意拉开梯度。

子代理调度模式 Subagent Scheduling Patterns

一句话：把子代理调度抽象为四种可复用模式（目标驱动 / 并行探索 / 实验运行 / 验证），并规定子代理提示词五要素契约。
EN · table
PatternUseKey idea

B Parallel explorationcomplex sub-problemsfire multiple agents in one message: investigation, refutation, cross-domain analogy
C Experiment runlong compute jobsstart minute-level polling right after submit: auto-diagnose errors, fix, resubmit
D Verificationpost-iteration QAan independent subagent audits the evidence chain of findings
ZH · table
模式用途核心思想
A 目标驱动（Goal-driven）研究迭代注入已尝试过的方向，要求产出可验证的发现（verifiable findings），并回写至 findings.jsonl
B 并行探索（Parallel exploration）复杂的子问题在同一条消息中并发启动多个代理：调查（investigation）、反驳（refutation）、跨领域类比（cross-domain analogy）
C 实验运行（Experiment run）长时计算任务在提交后立即开启分钟级轮询（minute-level polling）：自动诊断错误、修复并重新提交
D 验证（Verification）迭代后的质量保证（QA）由一个独立的子代理审计发现的证据链（evidence chain）
四种模式按「何时启动 / subagent 是否独立」两维度区分：A 单 agent 串行迭代；B 同一消息内并行扇出多个 agent，用于对抗式/多视角探索；C 用于长任务，靠轮询做 watchdog；D 事后独立审计，刻意用「未参与产出」的 agent 以降低自我证实偏差。
ENA subagent prompt should include: background, a verifiable deliverable, working directory, file/line caps, and completion criteria.
ZH一个子代理的提示词（prompt）应当包含：背景（background）、一个可验证的交付物（verifiable deliverable）、工作目录（working directory）、文件/行数上限（file/line caps），以及完成判据（completion criteria）。
五项是 subagent 提示词的最小契约：background 让 agent 不依赖会话历史（呼应 §9「State is injected via files」）；verifiable deliverable + completion criteria 把「完成」从主观判断变为可检查条件；working directory + file/line caps 是工程约束（呼应 §9「no single file over 300 lines」），防 agent 写超大文件污染状态。

设计意图

把「如何调用子代理」抽象成四种可对号入座的模式，而非泛谈「多智能体协作」。两个工程意图：① 让 orchestrator 派活时有明确决策树——按任务形态选模式，避免随手 spawn 导致的认知循环和 stall；② 用一句话强制规定 subagent 提示词的最小契约，把不可控的 agent 行为锁在可审计、可重放的边界内。

§ 9

工程约束 Engineering Constraints

一句话：六条工程红线——5 文件/300 行、状态经文件注入、迭代间强制验证、每 20 条核验、多样性优先、外部失败必升级。
EN1. At most 5 large files per iteration; no single file over 300 lines.
ZH1. 每次迭代（iteration）最多 5 个大文件；单个文件不得超过 300 行。
控制单次迭代的「改动面」与「单文件复杂度」。5 文件上限防一次改动牵连过广、难回滚；300 行上限防单文件膨胀到 context compaction 也吞不下——与 §3「fresh session over resume」配合，保证下次迭代注入时文件仍可被完整读取。两条都是抗认知循环和抗运行时脆弱的物理边界。
EN2. State is injected via files, not conversation history.
ZH2. 状态（State）通过文件注入，而非通过对话历史（conversation history）。
§2.4 和 §3 的核心设计重申：状态必须落盘到文件，而非依赖对话历史。原因——对话历史会在 context compaction 时被静默裁剪，导致循环「失忆」断裂。
EN3. Validation (test / compile / check) must run between iterations.
ZH3. 验证（Validation：测试 / 编译 / 检查）必须在迭代之间运行。
「between iterations」指两次迭代之间，不是可选。强制在每次迭代之间跑测试/编译/检查，尽早捕获失败、防错误状态累积写入 findings/state 污染后续迭代。与 §8 Pattern C/D 衔接：验证是机械化的独立步骤，不依赖 agent 自检。
EN4. Citation-like content is verified every 20 entries, never batched up.
ZH4. 类引用内容（Citation-like content）每 20 条核验一次，绝不积攒到大批量一起处理（never batched up）。
针对 LLM 捏造引用这一已知缺陷（§10 Limits 第 3 条明说错误源在模型本身）。规则要求每累积 20 条类引用内容就核验一次。理由：批量核验时单条错误成本高、回溯链长；分散到每 20 条能把核验变成流程中的常规机械步骤，前置而非事后补救。
EN5. With multiple candidate directions, prefer adding diversity over digging one deeper.
ZH5. 存在多个候选方向（candidate directions）时，优先增加多样性（diversity），而非把某一个方向挖得更深（digging one deeper）。
与 §3「Enforced direction diversity」、§6「Direction diversity」一脉相承。当存在多个候选方向时，优先扩展多样性而非深挖某一个。这是对抗认知循环的直接策略——重复深挖同一方向是局部最优陷阱的典型表现。
EN6. Unresolvable external-dependency failures escalate (full report + notify the owner + poll for a reply); never abandon silently.
ZH6. 无法解决的外部依赖失败（external-dependency failures）必须升级处理（escalate）：提交完整报告 + 通知所有者（owner）+ 轮询等待回复（poll for a reply）；绝不静默放弃（never abandon silently）。
「abandon silently」（静默放弃）正是 §1 中 stalling 和 runtime fragility 的隐蔽来源：失败被默认吞掉、看起来还在跑实则已停。escalate 三步：写完整报告 + 通知 owner + 轮询等回复——确保人类介入，把不可解的外部故障交还给人。

设计意图

把前文（§2–§8）的动机层论证收口为 6 条可机械执行的工程红线。三层意图：① 约束单次迭代的「物理面」（文件数、行数、状态载体、校验时机）——都是不依赖模型自律、可由外部强制的客观边界，呼应 §10「职责分离依赖协议约束而非模型自律」；② 把 LLM 已知缺陷（捏造引用、认知循环、静默失败）的缓解步骤前置为流程中的常规动作；③ 对外部不可控故障明确「绝不静默放弃」的处置路径。

「Separation of duties」依赖协议约束（protocol constraints），而非模型自律（self-discipline）。一旦移除约束，越界行为（overstepping behavior）会立刻复现——反向证明约束机制的必要性，也警告用户不要随意裁剪协议。这是整套约束的元原理：不能依赖 agent 自我克制，必须用结构性约束把正确行为变成唯一可行路径。

设计意图

整份协议的「诚实声明」：把框架能做什么、不能做什么、分数该怎么读，全部摊开。三层意图：① 用四篇论文 + 自评分数证明框架在多种异构任务上确实跑通，给可量化产出证据；② 用四条 Limits 主动圈定分数有效范围（仅协议内纵向可比，非对外质量声明），杜绝被误读为「顶会级成果」；③ 明确把幻觉与越界归因到 LLM 固有属性，强调框架作用是「用流程约束兜住模型的不可靠性」，而非消除它。
