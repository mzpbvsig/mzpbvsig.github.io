Claude Code 的 Phase / Task / Sprint 清单 · 真实用法

很多人会把需求拆成 Phase（阶段）→ Task（原子任务）→ 勾选清单 写进一个 tasks.md，让 Claude Code 逐条实现、边做边打勾。下面是逐字、来自真实仓库的两种主流形态（含一份真正用过、已打勾的文件），右侧配中文讲解。它是 spec 接力里"③ tasks"那一环的具体长相。

真实性说明：下面的 markdown 块均为从公开仓库逐字拉取，未改写。两种约定：① GitHub 官方 spec-kit（agent 无关，含 Claude Code）；② 社区 Pimzino/claude-code-spec-workflow（专为 Claude Code）。注意：这跟 Claude Code 自带的任务系统（~/.claude/tasks/ / TodoWrite）是两回事——这里讲的是"你写进仓库、用来驱动 agent 的 markdown 清单"。
需求 → 设计 → 任务清单(tasks.md) → 实现 spec.md design.md Phase→Task→[ ] 逐条做、打勾[x]、跑测试 ↑ 本文讲的就是这一格

形态 1 · GitHub spec-kit 官方模板（Phase + 任务ID + 并行/故事标记）

官方逐字templates/tasks-template.md（节选，原样）github/spec-kit ↗
## Format: `[ID] [P?] [Story] Description`
- **[P]**: Can run in parallel (different files, no dependencies)
- **[Story]**: Which user story this task belongs to (e.g., US1, US2, US3)
- Include exact file paths in descriptions

## Phase 1: Setup (Shared Infrastructure)
**Purpose**: Project initialization and basic structure
- [ ] T001 Create project structure per implementation plan
- [ ] T002 Initialize [language] project with [framework] dependencies
- [ ] T003 [P] Configure linting and formatting tools

## Phase 2: Foundational (Blocking Prerequisites)
**Purpose**: Core infrastructure that MUST be complete before ANY user story
**⚠️ CRITICAL**: No user story work can begin until this phase is complete
- [ ] T004 Setup database schema and migrations framework
- [ ] T005 [P] Implement authentication/authorization framework
- [ ] T007 Create base models/entities that all stories depend on
**Checkpoint**: Foundation ready - user story implementation can now begin in parallel

## Phase 3: User Story 1 - [Title] (Priority: P1) 🎯 MVP
**Goal**: [Brief description of what this story delivers]
**Independent Test**: [How to verify this story works on its own]
### Tests for User Story 1 (OPTIONAL - only if tests requested) ⚠️
> **NOTE: Write these tests FIRST, ensure they FAIL before implementation**
- [ ] T010 [P] [US1] Contract test for [endpoint] in tests/contract/test_[name].py
### Implementation for User Story 1
- [ ] T012 [P] [US1] Create [Entity1] model in src/models/[entity1].py
- [ ] T014 [US1] Implement [Service] in src/services/[service].py (depends on T012, T013)
**Checkpoint**: User Story 1 should be fully functional and testable independently
中文讲解：这套约定把工作切成 Phase 1 搭基建 → Phase 2 阻塞性地基 → Phase 3+ 每个用户故事一个阶段。每条任务带：
标记含义
T001任务唯一 ID，方便引用与表达依赖
[P]可并行（改的是不同文件、无依赖）——给并行执行用
[US1]归属哪个用户故事（User Story 1），让每个故事能独立实现/测试/交付为 MVP 增量
(depends on T012, T013)显式依赖：被依赖项没完成就不能动
**Checkpoint**检查点：到这儿该能独立跑通、可验证
- [ ]勾选框，做完改成 - [x]
顺序纪律（逐字）："Write these tests FIRST, ensure they FAIL before implementation" —— 先写测试、确认失败，再实现（TDD）；且 models → services → endpoints 的顺序。

形态 2 · Pimzino/claude-code-spec-workflow（原子任务 + Leverage/Requirements 回链）

社区逐字.claude/templates/tasks-template.md（节选，原样）Pimzino ↗
## Atomic Task Requirements
- **File Scope**: Touches 1-3 related files maximum
- **Time Boxing**: Completable in 15-30 minutes
- **Single Purpose**: One testable outcome per task
- **Specific Files**: Must specify exact files to create/modify

## Good vs Bad Task Examples
❌ "Implement authentication system" (affects many files, multiple purposes)
✅ "Create User model in models/user.py with email/password fields"

## Tasks
- [ ] 2. Create base model class in src/models/FeatureModel.ts
  - File: src/models/FeatureModel.ts
  - Implement base model extending BaseModel class
  - Purpose: Provide data layer foundation for feature
  - _Leverage: src/models/BaseModel.ts, src/utils/validation.ts_
  - _Requirements: 2.1_
- [ ] 3. Add specific model methods to FeatureModel.ts
  - File: src/models/FeatureModel.ts (continue from task 2)
  - Implement create, update, delete methods
  - _Requirements: 2.2, 2.3_
中文讲解：这套更强调"原子任务"——每条只碰 1–3 个文件、15–30 分钟能完成、单一可测产出、必须写明确切文件路径。每条任务额外带两条回链：
字段含义
File:本任务要创建/修改的确切文件
Purpose:这步要达成的单一目的
_Leverage: …_可复用的现有代码（让 Claude 别重造轮子）
_Requirements: X.Y_回链到 requirements 文档的需求编号，保证可追溯

清单是怎么被"驱动"的（实现阶段循环）

社区逐字Requirements → Design → Tasks → Implementation
Pimzino 工作流原话：用 Requirements → Design → Tasks → Implementation 驱动新功能（bug 则走 Report → Analyze → Fix → Verify）。到实现阶段，对 每一条任务循环：
for 每条 task in tasks.md: Implement → Review → log-implementation → Mark completed([x]) 实现 审查 记录实现 在清单里打勾
每个阶段之间有审批闸门(approval gate)：Requirements/Design/Tasks 各自要你点头才进下一步。这把"大功能"切成"可逐条验收、可随时中断续接"的流水。

怎么用它对齐需求：大功能在 spec 接力的"③ tasks"环节，让 Claude 产出这种 tasks.md（带 Phase、确切文件、依赖、Requirements 回链、勾选框）；实现时让它逐条做、做完打 [x]、每条跑验证，并在阶段闸门处停下等你确认。这样长任务可中断可续接、每步可验收。

诚实边界：① 这两套是社区/工具包约定（spec-kit 是 GitHub 官方工具包但 agent 无关；Pimzino 是社区），不是 Claude Code 内置强制格式。② Claude Code 另有自带的任务追踪（~/.claude/tasks/、TodoWrite，支持依赖/阻塞/跨会话），与本文的 markdown 清单是两套东西——可配合用，但别混为一谈。
