一句话本质

长程自主 agent 的可靠性来自工程脚手架而非模型能力——用状态外化把对话降级为缓存、用独立监督消除自评偏差、用分层看门狗覆盖静默死亡、用强制多样性与结构转向逃逸局部最优，并始终把人类降级为异常处理器而非必经节点。

看场景可省 · 前提

本方法论默认任务满足两个前提：① 无人值守（人不在关键路径上）；② 任务允许「重启 / 回滚」而非「绝不失败」。生产运维中不可回滚的高风险动作（删库、对外通知、schema 迁移）必须保留人类授权门——见 §7 通用性边界。

01

三大失败模式（设计起点）

整套方法论不是从理论推导，而是从三类经验失败归纳。每一条机制都能追溯到下面之一。这是世界观基线——原文明确：共同原因是缺少工程脚手架，不是模型能力不足。

"The common cause of all three is missing engineering scaffolding, not insufficient model capability. Every mechanism in this framework targets the failure modes above."
— SKILL.md §1 Motivation · framework.html
官方逐字 ① 认知循环（Cognitive Loop）

连续迭代尝试相似方向、收益递减，无法自行逃出局部最优。本质算法/搜索问题——单点无法自拔。

"successive iterations try similar directions with diminishing returns, unable to escape a local optimum on their own"
官方逐字 ② 停滞（Stalling）

agent 做完一段就输出摘要、等待用户反馈。外部看会话还活着、轮询还在跑，但工作已实际停止。本质语义/边界问题——比崩溃更常见。

"Externally the session looks alive and polling runs, but work has effectively stopped. Run logs show this is more common than crashes."
实践补充 · 优先级依据原文承认「停滞比崩溃更常见」——因此监控资源应优先投入「内容启发式停滞检测」（最后输出是问句 / 无增量），而非只做活性崩溃检测。任何长程 agent 仪表盘，停滞类告警优先级应高于崩溃类。
官方逐字 ③ 运行时脆弱（Runtime Fragility）

context compaction 静默打断循环；关闭会话会带走寄生其上的定时器。失败默认不被察觉。本质系统/运维问题——隐蔽死亡。

"context compaction silently breaks the loop; closing a session takes down the timers parasitic on it. Failures go unnoticed by default."
02

通用设计原则（12 条 · 对抗验证修正后）

原 skill 的 5 条行为约束 + 6 条工程约束 + 关键架构决策，剥离 research 语义后归纳为这 12 条。每条标注：原文出处（附英文）、为什么、迁移示例。其中 ⚠️边界 标注的是对抗验证发现的过度泛化点——套用前必须确认适用条件。

P1状态外化 / 进程无状态化官方逐字实践补充

定义把工作内存从易失的对话上下文迁移到持久化、可注入的介质，使每个工作单元成为无状态、可重启的节点。

为什么对话上下文既是认知循环的载体（旧推理污染新决策）又是运行时脆弱的根因（compaction 一发生循环就静默死亡）。把状态搬到比运行载体更持久的介质，使「重启」成为廉价日常操作而非灾难恢复——与数据库 WAL、systemd restart、k8s 无状态 pod 同构。

"Persist state to files — all progress is written to state/ files, not conversation memory. Each iteration starts a fresh session, injecting only curated state; never use resume."
"context accumulation is the primary cause of cognitive loops"
— SKILL.md §2.4 BC4 / §3 / §9.2 EC2 · source

迁移持续开发 agent：每个迭代结束把「当前 backlog / 已合入 PR / 已知回归失败」写入 repo-state.json，下次会话 fresh 启动只读该文件，不靠对话回忆昨天的进度。

P2执行 / 评价分离官方逐字

定义把「评价者」与「执行者」解耦到不同进程/会话，评价基于量化指标而非主观判断。

为什么模型存在自我确认偏差，倾向于认为自己仍在进展（要么过乐观继续死磕、要么过悲观轻易放弃）。把判停权交给不做事的层，基于硬指标决策，才能客观区分「真在跑」与「假装在跑」。

"Separate execution from evaluation — the agent doing the work does not judge its own progress; stall determination is made by the orchestration layer based on quantitative metrics."
— SKILL.md §3 · source

迁移运维自愈 agent：执行层负责重启/扩容/回滚；独立 SLO 评测层只读监控指标（错误率/延迟）判定「是否恢复」，执行层无权宣称自己成功。

P3结构性转向优于战术调参官方逐字⚠️ 边界

定义当参数空间内寻优连续失败时，应跳跃到更高层的结构空间搜索（换环境/框架/约束），而非在同一框架内更用力调参。

为什么在同一吸引盆地里做梯度下降只会原地打转。「连续失败次数」是从「局部搜索」切换到「结构重构」的硬阈值信号，与演化计算中「突变率随停滞升高」异曲同工。

"stale_count >= 2 → change a structural constraint, not tactical parameters ... the decisive gain usually comes from correcting the environment/structural constraint itself, not from tuning strategy parameters harder inside the existing frame."
— SKILL.md §6 · source

迁移持续集成 flaky 测试：连续 2 次只调 retry/超时（战术）无效时，应换测试运行器、拆微服务、改数据隔离（结构），而不是再加一次 retry。

⚠️ 边界 · 仅适用于多盆地搜索任务对抗验证发现：本原则仅适用于「多模态/多吸引盆地」的探索式任务（研究、架构选型、根因排查）。对确定性收敛任务（生产 bug 修复、ETL）——根因只有一个、正确解只有一个——强行「结构转向」（换框架/换架构）是浪费甚至制造故障。诊断原语：任务是否有「唯一正确解」决定是否套用。对收敛式任务改为「根因深挖优先（5-why、二分定位），穷尽根因空间后才升级结构层」。
P4分层冗余 + 故障域正交的看门狗官方逐字⚠️ 边界

定义用多个依赖关系正交、互不依赖的独立监督层互相覆盖单点失效，任一层死亡都能被其他层发现恢复。

为什么业务循环本身不可靠；任何单一守护层（含寄生在会话上的定时器）都会随会话关闭被一起带走。关键不是堆三份冗余，而是让三层的失效模式不重叠——任一种死法都有存活者能发现。与 k8s 多级探针、Apollo 三余度飞控同构。

"Three mutually-checking layers ... L0: resident shell guard (no session) / L1: durable cron, hourly (a living session) / L2: business loop (each its own session). Any one layer dying can be detected and recovered by another."
— SKILL.md §7 · source

迁移数据管道：L2=job 内部回调首行写心跳；L1=Airflow scheduler 每小时查各 job 心跳并重启；L0=独立于调度器的常驻进程，调度器本身死亡时由它拉起。

⚠️ 边界 · 抽象为 N≥2 层对抗验证发现：L0/L1/L2 预设了特定运行环境（有 resident shell guard、能起 headless agent、有 durable cron）。在托管 SaaS（Vercel/Lambda/Cloud Run）里无法直接落地。正确抽象：「至少存在两个失效模式不重叠的监督层（N≥2，按环境能力取最大）」。Serverless 场景：外部独立监控（UptimeRobot/Datadog）作 L0、平台 cron 作 L1、函数回调作 L2。
P5强制多样性 / 反早熟收敛官方逐字实践补充

定义维持「已尝试集合」，强制新尝试与集合全部元素相异（不是「尽量不同」而是「必须不同」），停滞后注入结构化扰动以逃逸局部最优。

为什么模型天然倾向在熟悉区域贪心搜索，没有显式约束会反复试相似方向、收益递减。等价于模拟退火需要「温度」、遗传算法需要「变异算子」——任何搜索型长程任务都需要反贪心机制。

"Enforced direction diversity — a new direction must differ from all history ... after a stall, inject a perturbation strategy ... prefer adding diversity over digging one deeper."
— SKILL.md §3 / §6 / §9.5 EC5 · source

迁移内容生产 agent：维护 topics_tried.json，每篇新选题必须与历史在主题/角度/体裁全部不同；连续两篇互动下降时注入「反观点选题」或「跨域类比选题」扰动。

P6自主性边界 / 默认即执行官方逐字⚠️ 边界（最高优先级）

定义把人类从「必经节点」降级为「异常处理器」：进入自治区间后不等待外部输入，歧义自行裁决并审计，可逆的常规操作无需确认。

为什么在长程无监督系统里，「暂停等确认」不是谨慎而是停机伪装。依赖人类即时反馈 = 退化成有监督的短任务。

"Zero interaction — no prompting the user during a run: no Plan Mode, no question tool, no ending on a question ... Ready means execute — the most common hidden violation: finishing all preparation and then asking 'should I submit?'."
— SKILL.md §2.1 BC1 / §2.2 BC2 · source

迁移持续部署 agent：测试通过即自动部署到 staging，不问「要不要部署」；只有部署失败且自动回滚也失败时才升级通知 oncall。

⚠️ 边界 · 必须加「爆炸半径」维度（对抗验证 high 优先级）本原则只适用于可逆/低爆炸半径动作。生产运维中大量操作不可回滚（删数据、发用户通知、停付费实例、改 schema、对外公告）——对它们照搬「默认即执行」是灾难。可逆性三级分类：
  • reversible（可回滚：部署、配置）→ 执行-回滚，无需确认
  • compensable（可补偿：发通知→再发更正）→ 执行-通知，事后告知
  • irreversible（不可逆：删库、schema 迁移、对外公告）→ 请求-授权，保留人类门
即便对 irreversible 动作，仍应消除「问句结尾」式停滞——把授权做成显式 gate，而非 conversational stall。
P7分级负反馈 + 阶梯式升级官方逐字✏️ 阈值修正

定义偏差量级决定纠偏层级：小偏差就地纠正、中偏差换结构约束、大偏差升级人类。阈值刻意梯度化——低成本错误早抓、高成本动作晚动。

为什么任何闭环控制器都应有多档响应而非单一动作。自愿性停滞廉价可逆应早抓，结构性卡死需换框架应慎重，人类介入成本最高应最后动——控制论的分层调度律。

"stale_count >= 2 → change a structural constraint, not tactical parameters; >= 4 → flag for human attention ... The 2h threshold is deliberately shorter than the 4h stuck-task threshold."
— SKILL.md §6 / §7 · source

迁移监控告警：P3 告警 5 分钟自愈脚本处理；连续 2 次自愈失败→改配置/扩容（结构层）；连续 4 次失败或影响 SLO→page oncall。

✏️ 忠实性修正 · 阈值与升级链对抗验证发现方法论初稿凭空加了「≥1 告警」档、并把「4h stuck-task」错挂到「升级人类」。修正后：① stale_count 仅 ≥2 触发结构转向、≥4 触发人类升级——无 ≥1 档；② 「4h stuck-task」触发的是结构性重开（换框架/方向）而非人类升级；③ 人类升级仅由 stale_count≥4（计数）触发，不由时长直接触发。④ 原文 §5 另写「stale_count>=3 generate a fresh direction」与 §6 的 >=2 存在内部不一致——采用者需自行裁定并统一。
P8最小权限监督者 + 封闭动作集官方逐字

定义监督组件只能对被监督对象执行预定义的白名单动作，禁止读写其业务数据或代其发声，把失败半径收窄。

为什么若监督者能任意读写工作层状态，监督者自己出错时会污染被监督者，引入新的脆弱源（网页补充：一次巡检越界造成上下文污染、上报漂移、并发写风险）。封闭动作集让监督者既能救火又不能篡权——多 agent/多进程系统的安全边界。

"a heartbeat patrol may take only three actions on tasks that aren't its own: liveness-check, restart, nudge. It does not read their data, modify their state, or report for them."
— SKILL.md §2.5 BC5 / Limits #4 · source

迁移多服务运维平台：监控服务对业务服务只能调 health endpoint、触发 restart、发轻量提醒，不能读业务数据库、不能改业务配置、不能代业务发用户通知。

P9工作单元硬上限 + 迭代间强制验证官方逐字⚠️ 边界

定义每个工作单元设资源预算和时长天花板，强制定期交还控制权，并对已知易腐产物高频小批量校验。

为什么单次工作单元无界膨胀会拖垮全局（上下文爆炸/成本失控）；错误若不在迭代边界被拦截会层层放大成结构性偏差。CI 的「每构建即验证、fail fast」在 agent 迭代层的映射。

"At most 5 large files per iteration; no single file over 300 lines ... a single work session caps at 15 rounds or 30 minutes ... Validation must run between iterations ... Citation-like content is verified every 20 entries, never batched up."
— SKILL.md §9.1 EC1 / §6 / §9.3 EC3 / §9.4 EC4 · source

迁移长文档翻译 agent：每个会话最多译 3000 字即收尾保存；每段后跑术语一致性检查；每 20 段跑一次全篇术语/数字核验，不积压到最后。

⚠️ 边界 · 数值是示例标定对抗验证发现：「15 轮/30 分钟、5 文件/300 行、每 20 条」都是研究任务迭代粒度的偶然标定，不是通用常量。重标方法：时间窗 ≈ k × 单次工作单元典型耗时（k≈3–5 留余量），且必须 < 业务对该工作单元的 SLA。实时任务：硬截止=SLA 的 50%；大计算任务：改用「检查点间隔」而非「会话时长上限」。核验频率应 > 单产物「潜伏到爆发」的时长。
P10绝不静默失败 / 故障必升级官方逐字

定义不可恢复的错误必须升级（完整报告 + 通知 owner + 轮询回复），禁止把外部依赖失败静默吞掉导致任务表面继续实际空转。

为什么silent failure 是分布式系统最危险的故障类别。无监督长程运行中，外部依赖失败若被吞掉，任务会表面继续实际空转，整条产物链可能基于缺失数据。

"Unresolvable external-dependency failures escalate: full report + notify the owner + poll for a reply; never abandon silently."
— SKILL.md §9.6 EC6 · source

迁移ETL 数据管道：上游 API 重试 N 次仍失败，必须写死信队列 + 通知数据 owner + 定时轮询恢复，绝不静默跳过该批次让下游仪表盘悄悄显示错误数据。

P11回调即报活（进程内自检自愈）官方逐字补全 · 升格为独立原则

定义每个长循环的恢复入口（尤其 context compaction 后），第一动作必须是：① 刷新自身 last_seen；② 自检活性；③ 失败立即重启并记录。业务逻辑排在报活之后。

为什么对抗验证指出：这条原被埋在可靠性清单里，但它其实是与分层看门狗不同层级的自愈原语——它是进程内的自检自愈（防 compaction 静默死，对应 L2），而看门狗是进程外的兜底恢复（L0/L1）。混淆两者会误判防护层级。

"Callback means report-alive — after context compaction the loop dies silently. The first action of every callback is to update its own last_seen, then check liveness; on detecting failure it restarts immediately and logs it."
— SKILL.md §2.3 BC3 · source

迁移任何被 compaction/restart 影响的长循环（webhook 处理器、长轮询 worker），恢复后首条指令 = 刷新活性戳 + 自检 + 失败即重启。

P12可委派工作单元契约官方逐字补全 · 完备性缺口

定义每个被委派的无状态工作单元，其委托规格必须包含五要素：背景 / 可验证交付物 / 工作目录 / 资源·规模上限 / 完成标准。

为什么对抗验证（完备性 critic）发现这是原 skill 的硬洞察却被方法论漏掉——它是无状态工作单元的入场券，与 P1（状态外化）是一对：P1 定义「状态如何进」，P12 定义「任务如何被指定」，缺一不可。

"A subagent prompt should include: background, a verifiable deliverable, working directory, file/line caps, and completion criteria."
— SKILL.md §8 末句 · source

迁移运维恢复子代理：背景=故障上下文；交付物=恢复后 health check 通过；工作目录=受影响服务；上限=最多 N 次操作；完成标准=SLO 恢复且维持 10 分钟。

03

五层架构

原 skill 的两层（编排/执行）+ 状态层，补全后抽象为五层。每层职责单一、边界封闭，层间只通过文件通信，无共享内存、无直接调用。

┌─ 编排层 Orchestrator（监督控制层）──────────────────────┐ │ 读 state → 检测停滞（量化指标）→ 生成新方向 → 启动/重启/nudge worker │ └──┬──────────────────────────────────────────────────────────┘ │ （只写 state 文件，不直接调用 worker 内存） ▼ ┌─ 执行层 Worker（各任务 fresh session，无状态、可重启）────────┐ │ 接受注入的目标+状态 → 执行 → 产可验证交付物 → 写回 state │ └──┬──────────────────────────────────────────────────────────┘ │ ← 三层看门狗在外部巡检活性（不读写 worker 业务数据） ▼ ┌─ 持久状态层 state/ 文件系统（层间唯一契约）─────────────────┐ │ task_spec.md · progress.json · findings.jsonl(append-only) │ │ directions_tried.json · iteration_log.jsonl ＋ logs/{work,orch,heartbeat}.jsonl │ └─────────────────────────────────────────────────────────────────────┘ ▲ 巡检结果 / 升级报告 ┌─ 看门狗层 Watchdog（L0 常驻 / L1 cron / L2 回调，依赖关系正交）┐ │ 只做三件事：liveness-check / restart / nudge（封闭动作集） │ └─────────────────────────────────────────────────────────────────────┘ ┌─ 人类异常处理层（stale_count≥4 或不可自愈外部失败时才调用）────┐ │ 异常处理器，非必经节点；零交互已把人移出关键路径 │ └─────────────────────────────────────────────────────────────────────┘
实践补充 两个关键不对称

① 停滞判定是单向的（编排层用定量指标判 worker 停滞），看门狗三向检查是对称的（L0/L1/L2 任一层死都能被另一层发现）——前者解决局部最优，后者解决单点故障，是两种不同的控制论问题，刻意分开处理。

② 状态文件是唯一的层间耦合点：所有交互通过标准化文件进行，没有任何进程间直接通信——使任何一方都可被替换、重启、人工接管而不破坏协议。文件即消息队列。

反馈环检测信号纠正动作阈值 / 升级
① 停滞计数负反馈
官方逐字		 迭代级：单次迭代 0 新产物 或 定量指标下降 stale_count+1；≥2 改结构约束（Pivot structure）；≥4 升级人类 无 ≥1 档（✏️修正）。连结构重构都失败→任务定义本身需重写，由人类层处理

多样性机制（7 条）

  1. 显式已尝试集合：维护 directions_tried.json（或等价「已尝试解空间分区」列表），作为强制差异化的依据。
  2. 硬约束差异化：新尝试必须与全部历史元素相异——不是「尽量不同」而是「必须不同」。
  3. 停滞后扰动注入：stall 后主动注入结构化扰动（反假设、跨域类比、对立视角）。
  4. 结构转向而非深挖：stale≥2 改结构约束，不继续深挖——换吸引盆地而非原地梯度下降。
  5. 多候选偏好多样性：多候选并存且当前最优收益递减时，优先扩宽搜索面而非加深当前最优（探索优于利用）。
  6. 上下文周期性清空：fresh session over resume，防上下文累积导致在熟悉区域反复采样（认知层面的多样性维持）。
  7. 并行扇出异构视角：一条消息内扇出调研/反驳/跨域类比多个异构 agent，从结构上保证探索的异构性。

06

迁移到非研究任务

实践补充 极易迁移（架构模式，零领域依赖）
  • 状态外化 + 进程无状态化（文件即层间契约）
  • 执行/评价分离（工作者不自评，编排层基于量化指标判停）
  • 分层冗余看门狗（N≥2 层依赖正交）
  • 分级负反馈 + 阶梯式升级阈值（控制论分层调度律）
  • 结构性转向优于战术调参（通用搜索空间升级，仅限多盆地任务）
  • 强制多样性（已尝试集合 + 新尝试必须全异 + 扰动注入）
  • 零交互 / ready 即执行 / 回调即报活（事件驱动系统的活性纪律）
  • 最小权限监督者 + 封闭动作集
  • 工作单元硬上限 + 迭代间强制验证
  • 绝不静默失败 + 外部依赖升级
  • 按写者分离的独立日志流 + append-only 产物流
看场景可省 · 必须按领域定制 机制通用，但参数/语义必须重标
  • 停滞指标：research 用「新发现数」。开发→「合入 PR 数/通过的测试数」；运维→「处理的告警数/MTTR」；内容→「产出成品数/互动指标」。维持型任务（健康服务本就没有「新发现」）需改为「健康持续时长/SLO 达成/队列积压」——见 §7 反例。
  • 核验对象与频率：「每 20 条引用」的 20 是经验值、引用是学术对象。开发→「每 N 次 commit 跑测试」；运维→「每 N 次变更审计」；内容→「每 N 条事实核查」。频率应 > 错误累积速率。
  • 「方向」语义：研究=假设/切入角度；开发=技术方案/架构选型；运维=根因假设；内容=选题角度。「已尝试的解空间分区」抽象可迁移，schema 要重设。
  • 验收标准：研究用论文体裁（页数/引用/自评）；运维→SLO/MTTR；开发→feature complete 清单/覆盖率。
  • 子代理调度模式角色：B（调研/反驳/跨域类比）与 D（审计证据链）是研究拆分。开发对应「实现/测试/文档」三路并行，验证换「code review/安全扫描」。模式（扇出+独立验证）通用，角色需重填。
  • 结构性转向的具体手段：研究是「对立假设/跨域案例」；开发是「换框架/换依赖/重构」；运维是「换根因假设层级」。
  • 所有时间阈值（15 轮/30 分钟、2h/4h、每小时巡检）：研究任务节奏调优。迁移到秒级交易、分钟级部署、小时级研究时都要按 SLA 重标。72h 是已验证最长运行记录，非可调阈值（✏️修正）。
  • 产物累积日志：findings.jsonl 的 append-only 模式通用，但「产物单元」语义需定制（研究=发现；开发=commit/PR；运维=incident；内容=draft 版本树）。

三个迁移示例

① 持续开发 agent（多盆地探索 + 可逆）

每迭代把 backlog/已合 PR/回归失败写 repo-state.json（P1）；编排层基于「新增通过测试数」判停滞（P2）；flaky 测试连 2 次调参无效→换运行器/拆服务（P3）；测试通过即自动部署 staging，回滚是执行-回滚的一部分（P6 reversible）；每 commit 跑测试 = 迭代间验证（P9）。

② 运维自愈 agent（维持型 + 部分 irreversible）

停滞指标改为「SLO 达成时长/队列积压」而非「新产物」（§7）；执行层重启/扩容，独立 SLO 层判恢复（P2）；删库/改 schema 归 irreversible，保留人类授权门（P6 三级分类）；外部依赖失败→死信队列+oncall（P10）；监控对业务只能 health/restart/nudge（P8）。

③ 数据 ETL（确定性收敛 + 异步作业）

不套用 P3 结构转向（根因唯一，改为根因深挖，§7）；作业提交即启动分钟级轮询、错误自诊断重提（反馈环⑦，完备性补全）；上游 API 失败重试 N 次后写死信队列+轮询（P10）；job 内回调首行写心跳（P11）；Airflow scheduler 作 L1、独立常驻进程作 L0（P4 N≥2）。

07

⚠️ 通用性边界与反例（对抗验证产出）

这是本方法论最有价值的一节——由「通用性对抗验证」把方法论套到运维/ETL/内容生产上找出的过度泛化点。套用前逐条确认。

⚠️ 边界 · high B1｜默认即执行 ≠ 对所有动作都不问

把「可逆常规操作从请求-授权改成执行-回滚」写成通用律，在生产运维里危险：删数据、发用户通知、停付费实例、改 schema、对外公告都不可回滚。判据=爆炸半径/可回滚性，分三级（reversible→执行-回滚 / compensable→执行-通知 / irreversible→请求-授权）。见 P6。

⚠️ 边界 · high B2｜结构转向只适用于多盆地搜索任务

生产 bug 修复、ETL 多是确定性收敛任务——根因唯一、正确解唯一，没有「多盆地」。强行「换框架/换架构」是浪费甚至制造故障。诊断原语：任务是否有「唯一正确解」。收敛式任务改为「根因深挖优先（5-why/二分定位），穷尽根因空间后才升级结构层」。见 P3。

⚠️ 边界 · high B3｜名义约束 ≠ 实际约束

方法论声称「协议约束而非模型自律」是结构性的，但协议约束本身仍由同一个模型执行——在无独立运行时强制的环境（如纯 Claude Code 会话内），约束可被模型自己绕过，「结构保证」是名义的而非实际的。区分：「名义约束」（写在 prompt/skill 里，靠模型遵守）vs「实际约束」（由独立运行时强制：OS 权限、CI 门禁、外部 linter）。只有实际约束才提供可靠性保证。迁移指南要求：每个关键约束都映射到一个独立运行时强制点，否则降级为「软约束」并降低可靠性声称。

⚠️ 边界 · medium B4｜停滞信号在维持型任务上系统性误报

「0 新发现→停滞」把「产物产出」当唯一信号，在维持型任务（运维、ETL）上误报：健康状态下本就没有「新发现」。泛化判定公式：stall ⟺ (无正向推进信号) AND (无系统健康信号)。两个条件同时满足才算停滞。产物型任务看增量产物；维持型任务看健康持续/SLO 达成/队列积压。

⚠️ 边界 · medium B5｜所有时间窗都是示例标定，需按 SLA 重标

15 轮/30 分钟、2h/4h 是研究任务迭代粒度的偶然标定，套到秒级运维太慢、套到天级内容生产太频繁。重标方法：时间窗 ≈ k × 单次工作单元典型耗时（k≈3–5），且 < 业务 SLA。实时任务：硬截止=SLA 的 50%；大计算任务：改用「检查点间隔」。见 P9。

⚠️ 边界 · medium B6｜分层看门狗预设了特定运行环境

L0/L1/L2 预设有 resident shell guard、headless agent、durable cron——托管 SaaS（Vercel/Lambda/Cloud Run）无法直接落地。抽象为：「至少两个失效模式不重叠的监督层（N≥2）」。Serverless：外部独立监控作 L0、平台 cron 作 L1、函数回调作 L2。见 P4。

实践补充 · 根本不对称生产运维的「错误」有真实业务损失（SLO 违约、数据损坏、用户可见故障），而研究的「错误」（捏造引用）主要是质量瑕疵。因此「reboot 而非 resume」「默认即执行」这类把可用性置于正确性之上的取舍，在研究语境合理、在生产语境常常是错的——这是判断每条边界时的心智模型。
08

诚实边界（Limits）

原 skill 作者自陈的四条局限。对通用方法论设计者尤其重要的是 Limit 1 与 Limit 4。

官方逐字 Limit 1｜自评分只是协议内纵向可比

论文 8.0–8.6 分来自框架内 multi-persona 模拟评审，只在该协议内纵向可比，不是外部质量声明。评估框架本身必须用框架外基准。

"Scores come from in-framework multi-persona simulated review; comparable only longitudinally within the same protocol, not an external quality claim."
官方逐字 Limit 2｜最长运行 72h（观测记录，非阈值）

72 小时是已验证最长连续运行记录（含 6 次方向性人类输入、零运维介入）——是参考上限，非可调阈值（✏️修正：勿与 15 轮/30 分钟/2h/4h 等真正可调阈值并列）。

"The longest continuous run on record was 72 hours, with 6 directional human inputs during it — zero operational intervention, directional intervention retained."
官方逐字 Limit 3｜框架不降低错误率本身

捏造引用/数据造假源自 LLM 本身，框架只是把外部核对变成流程里的机械步骤，并未移除错误源。系统降低的是停机/停滞概率，不是错误率。误以为「用了框架产物就自动正确」是危险的。

"Fabricated citations and data artifacts originate from the LLM itself; the framework makes external checking a mechanical step in the process, it does not remove the error source."
官方逐字 Limit 4｜职责分离依赖协议约束，撤约束即失效

分离职责靠协议约束而非模型自律，去掉约束越权行为立刻回来。这正是 §7-B3「名义约束 vs 实际约束」的根源。

"Separation of duties relies on protocol constraints, not model self-discipline; removing the constraints brings overstepping behavior back."
— SKILL.md §10 Limits · source

常见陷阱速查

陷阱对策
战术调参成瘾：同框架内反复失败只会更努力调参，不切结构空间（认知循环的伪装）stale≥2 切「状态空间」而非调参；对每个候选框架仍设硬上限（stale≥4）强制升级
隐蔽停滞：会话外部看着活着（polling 在跑、心跳在写），工作已停——比崩溃常见双层活性判定（时间戳>2h + 内容启发式=最后输出是问句）；独立看门狗外部巡检
静默死亡无察觉：compaction 或关会话悄悄带走循环与寄生定时器三层相互监督（依赖正交）+ 回调首动作报活 + 状态外化使重启廉价
准备就绪后等确认：「要不要提交？」是最常见隐性违规，本质是停滞伪装人类降为异常处理器（stale≥4 才上报）；禁止问句结尾；歧义自决并记 level=decision
依赖模型自律而非协议约束：撤掉约束越权立即复现用结构约束保证正确行为是唯一可行路径（fresh session/最小权限/文件注入）；把约束映射到独立运行时强制点
误以为框架降低错误率：捏造/错误源自模型，框架只把核对变机械步骤明确声明降的是停机/停滞概率不是错误率；易腐产物内建机械核验，频率>错误累积速率
监督者越权污染：巡检插手其它任务，造成上下文污染、上报漂移、并发写看门狗最小权限（封闭动作集）；独立量化评测交编排层；引入第三方验证子代理
日志跨文件关联困难 + 并发写冲突按写者分日志流（work/orchestrator/heartbeat 各一）；状态外化到单一可信文件；层间零共享内存
方向探索早熟收敛：多次迭代试相似方向、收益递减却无法逃出保留「已完成分区」集合 + 强制新尝试全异；停滞后注入结构性扰动
易腐产物积压核验：攒到最后批量核验，错误已扩散，修正成本指数级校验分摊（每 N 个产物即核验，禁积压）+ 迭代间强制验证
10

一页纸速查表

设计任何长程自主 agent 框架时，问自己这 10 个问题：

  1. 状态在哪？→ 必须落盘成可注入的最小集合，对话只是缓存（P1）。禁用 resume。
  2. 谁判停滞？→ 不能是干活的人。独立编排层基于量化指标（P2）。
  3. 连续失败怎么办？→ ≥2 换结构非调参（仅多盆地任务，P3+B2）；≥4 才升级人类。
  4. 谁看着循环别静默死？→ N≥2 层依赖正交的看门狗（P4）；进程内回调首动作报活（P11）。
  5. 怎么防止反复试同方向？→ 已尝试集合 + 新尝试必须全异 + 扰动注入（P5）。
  6. 哪些动作能不问人就做？→ 仅 reversible。irreversible 保留人类门（P6+B1 三级分类）。
  7. 纠偏有几档？→ 就地纠 / 换结构 / 升级人类，阈值梯度化（P7）。
  8. 监督者能干什么？→ 只能 liveness-check/restart/nudge，封闭动作集（P8）。
  9. 工作单元有上限吗？→ 资源+时长硬上限，按目标 SLA 重标；迭代间强制验证（P9+B5）。
  10. 外部失败能静默吞吗？→ 永不。报告+通知+轮询（P10）。异步作业提交即轮询（反馈环⑦）。

每条约束映射到一个独立运行时强制点（OS 权限/CI/外部 linter），否则只是名义约束、可靠性声称要降级（B3）。

附

这套方法论是如何产出的

由一个 dynamic workflow（8 个 subagent，约 22 万 token，~11.5 分钟）产出，分三阶段：

  • 阶段 1 · 分析（4 维并行）：失败→机制映射 / 架构与执行流程解构 / 约束背后的工程原理 / 控制论系统论视角。每个维度独立深挖原 SKILL.md，输出「机制→抽象原理→是否可迁移」。
  • 阶段 2 · 综合：把 4 份分析合成通用方法论骨架（设计原则/架构层/反馈环/可靠性/多样性/陷阱/迁移性）。
  • 阶段 3 · 对抗验证（3 视角并行）：① 忠实性——核对每条抽象能否追溯到 SKILL.md 原文（揪出 5 处自行加档/误述）；② 通用性——套到运维/ETL/内容生产找反例（揪出 7 处过度泛化）；③ 完备性——查原 skill 哪些机制没被吸收（揪出 7 处缺口）。

本文档是应用全部验证修正后的版本：P3/P4/P6/P7/P9 加了边界标注，P11/P12 与反馈环⑦是补全，§7 整节来自通用性验证，阈值修正来自忠实性验证。三视角的 verdict 均为 needsRevision——本版即修正结果。
