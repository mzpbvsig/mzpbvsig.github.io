SPEC 文档怎么分类 · 要不要保存 · 存哪些文件夹

回答三件事：① 每个功能的 spec 怎么分类、② 文档要不要持续保存、③ 存到哪些文件夹。基于三套真实约定（Anthropic 官方 / GitHub spec-kit / Pimzino），标 官方逐字 的是原文引用。

官方逐字 实践补充 看场景
一句话先记住：一个功能 = 一个文件夹，夹里放「需求 / 设计 / 任务」三件套；持续保存并 check 进 git（它是"为什么有这段代码"的永久档案）；位置二选一 —— specs/001-功能名/（spec-kit，可见强排序）或 .claude/specs/功能名/（Pimzino，跟配置放一起）。

三个问题，直接答

问题答案
每个功能怎么分类一功能一夹。要排序用 001-短名；要语义用 功能名。夹内固定放需求/设计/任务三件套
要持续保存吗要，而且 check 进 git。它是 source of truth、"为什么代码长这样"的永久记录，新会话出问题可 pin 回来当恢复点
存哪specs/（spec-kit）或 .claude/specs/（Pimzino）；全局长期文件单独放 .specify/memory/ 或 .claude/steering/

最轻量① Anthropic 官方：只要 SPEC.md，不规定文件夹

项目根/ ├── SPEC.md # 访谈产出的规格 ├── PLAN.md # 计划，复查时拿它对照 └── CLAUDE.md
官方逐字 "start a fresh session to execute it... you have a written spec to reference."

适合单功能、小项目。文件直接放根目录，不分夹。

逐字证据② GitHub spec-kit：specs/ + 编号文件夹

"Each feature created generates a new numbered folder with the feature short name in the specs folder."
项目根/ ├── .specify/ # 系统盘（隐藏，别污染主视图） │ ├── memory/constitution.md # 项目宪法/原则（全局长期） │ ├── scripts/ # create-new-feature.sh 等 │ └── templates/ # spec/plan/tasks 模板 └── specs/ ├── 001-user-login/ # 一功能一编号夹 │ ├── spec.md # 目标 + 需求 │ ├── plan.md # 架构/方案 │ └── tasks.md # 原子任务 T001… ├── 002-oauth/ └── 003-payment/

分类法：编号 + 短名（001-user-login）—— 编号=创建顺序，天然排序、不重名。

证据：github/spec-kit ↗

逐字证据③ Pimzino：.claude/specs/ + 功能名文件夹

"spec-driven development for new features (Requirements → Design → Tasks → Implementation)."
项目根/.claude/ ├── steering/ # 跨功能指导文件（全局长期） │ ├── product.md # 产品方向 │ ├── tech.md # 技术栈 │ └── structure.md # 代码结构约定 ├── specs/ │ ├── user-login/ # 一功能一名字夹 │ │ ├── requirements.md # 需求：用户故事/验收标准 │ │ ├── design.md # 设计 │ │ └── tasks.md # 任务 │ └── oauth/ ├── bugs/ # bug 流程 Report→Analyze→Fix→Verify └── templates/

分类法：功能名（user-login）—— 靠语义，不靠编号。

证据：Pimzino/claude-code-spec-workflow ↗

关键区别：specs/ vs .claude/specs/

spec-kit specs/Pimzino .claude/specs/
位置项目根（可见）.claude/ 下（半隐藏）
分类001-编号-短名功能名
三件套spec / plan / tasksrequirements / design / tasks
全局文件.specify/memory/constitution.md.claude/steering/*.md
适合想可见、强排序、可审计想 spec 跟 Claude 配置放一起

实践变体进阶：按"生命周期"再分夹

有人在 specs/ 里再开状态夹，让"在做/已做"一目了然，做完就把功能夹挪过去：

specs/ ├── plans/ # 待办：高层架构决策 ├── in-progress/ # 在做：当前工作的"上下文锚点" └── plans-executed/ # 已做：为什么存在这段代码的永久史
证据：How to Structure .claude/ Folder ↗

怎么选（务实建议）

  • 单人 / 小项目 → 官方法，根目录 SPEC.md 就够，别上文件夹体系。
  • 想可见、强排序、给人审计 → spec-kit：specs/001-功能名/。
  • 想 spec 和 Claude 配置统一管 → Pimzino：.claude/specs/功能名/。
  • 功能多、要分在做/已做 → 叠生命周期夹（plans / in-progress / plans-executed）。
  • 铁律：全局长期文件（产品/技术/结构/宪法）放 .specify/memory/ 或 .claude/steering/，别塞进单个功能夹。
结论：一功能一夹（需求/设计/任务三件套）→ 持续保存 + check 进 git（永久档案、可作恢复点）→ 存 specs/ 或 .claude/specs/，全局文件单独放。
