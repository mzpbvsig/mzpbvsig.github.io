Claude Code「spec 接力」详解

把大功能的需求先写成一个自包含的 spec 文件，再换一个干净上下文的会话去实现——这就是"spec 接力(spec relay / handoff)"。本文讲清它的两种形态、具体做法、文件长什么样，并标注每条的真实证据来源。

一句话定义：需求 → 写成磁盘上的真实文件（spec/design/tasks）→ /clear 或新会话 → 新会话只读这份文件逐条实现、边做边更新状态、跑测试验收。
为什么要"接力"到新会话：同一会话里 Claude 带着写 spec 时的隐含假设，会不再逐字读 spec；新会话强迫它像新工程师一样从头逐字读。〔buildthisnow〕

形态 A · 手动 spec 文件 → 新会话（主流，证据最硬）

你显式让 Claude 写一个真实文件，自己能审能改，然后真正换新会话执行。官方推荐路径就是这种。
① 访谈挖需求 ② 编译成 spec 文件 ③ 换干净会话执行 ④ 自验证收口 AskUserQuestion → SPEC.md / spec.md → /clear 或新窗口 → 跑测试 / /goal 逐题反问 design.md tasks.md 只读 spec 实现 更新 tasks.md 状态 ─────────────────────────────────────────────────────────────────────────────── (深推理 · 可用 Opus) (清晰执行 · 可用 Sonnet)〔buildthisnow〕
官方逐字① 让 Claude 面试你，再写 SPEC.md（Claude Code 原生）
I want to build [brief description]. Interview me in detail using the
AskUserQuestion tool.

Ask about technical implementation, UI/UX, edge cases, concerns, and
tradeoffs. Don't ask obvious questions, dig into the hard parts I might
not have considered.

Keep interviewing until we've covered everything, then write a complete
spec to SPEC.md.

实践者·逐字同一模式的经典原型（Harper Reed，被 Simon Willison 转载背书）
头：一次只问一个问题，层层递进逼出完整规格——
Ask me one question at a time so we can develop a thorough, step-by-step
spec for this idea. Each question should build on my previous answers, and
our end goal is to have a detailed specification I can hand off to a
developer. Let's do this iteratively and dig into every relevant detail.
Remember, only one question at a time.

Here's the idea:
收口：把讨论编译成"开发者可直接开工"的规格——
Now that we've wrapped up the brainstorming process, can you compile our
findings into a comprehensive, developer-ready specification? Include all
relevant requirements, architecture choices, data handling details, error
handling strategies, and a testing plan so a developer can immediately
begin implementation.
Harper Reed 原文 ↗
实践者·逐字② 从 spec 再生成"实现蓝图 + 勾选清单"
拆成小步、强制 TDD、不允许复杂度跳变——
Draft a detailed, step-by-step blueprint for building this project. Then,
once you have a solid plan, break it down into small, iterative chunks that
build on each other... Prioritize best practices, incremental progress, and
early testing, ensuring no big jumps in complexity at any stage...
Can you make a `todo.md` that I can use as a checklist? Be thorough.
Harper Reed 原文 ↗
官方逐字③ spec 必须"自包含"才接得住
官方原则：spec 要点名涉及的文件/接口、写明 out of scope、结尾给端到端验证步骤。"把 spec 写精确，比盯着实现过程更值得花时间。"

④ 接力执行
写完 → 新窗口/新会话（干净上下文）→ 让它读 spec/tasks 逐条实现、边做边在 tasks.md 更新状态、跑测试。Harper 的做法是把 prompt_plan.md 里的 prompt 一个个粘进去（结对式），或整体丢给 Aider 自动跑测试。

spec 文件到底长什么样（三处证据互相印证）

来源文件形态章节 / 内容
官方Best practices SPEC.md（单文件，自包含） 点名文件/接口 · 写明 out of scope · 结尾端到端验证步骤
buildthisnow（教程站） "最小 spec 三段" requirements（用户故事+验收标准）· design（数据模型、API 契约、改哪些文件）· tasks（有序、每步列依赖）
Harper Reed 三文件 spec.md（详细规格）· prompt_plan.md（拆成一个个可直接粘的实现 prompt）· todo.md（勾选清单）
三阶段法（Armin 同款思路） 三文件 spec.md · design.md · tasks.md；实现阶段在 tasks.md 里逐条更新状态
共性：都把"要做什么/怎么设计/分几步"落到磁盘文件，让重要决定写下来、而不是留在模型脑子里——这正是"接力"能成立的物理基础。

形态 B · plan mode 的内部 plan 文件 注意：默认不是换新会话

很多人以为 plan mode = spec 接力，其实不完全是。区别要讲清。
  • 机制：plan mode（Shift+Tab / --permission-mode plan）下 Claude 只读不改，把计划写进自己的 plans 文件夹（一个 markdown）；退出 plan mode 时从磁盘读回那个文件再开工，你会先看到确认屏审批。〔Armin Ronacher〕
  • 计划里写什么：第一阶段探索得到的背景上下文（含文件名、代码路径追踪）、需求与约束、待修改关键文件的路径。〔Armin Ronacher〕
  • 关键差异/坑它是同一会话 approve→执行，并非干净上下文接力；而且 plan 文件藏在文件夹里、不好手动审改。〔Armin Ronacher〕
  • 结论：正因为上一条，Armin 和很多资深用户更偏向形态 A——自己控的磁盘 spec 文件，既能审改、又能真正换新会话。原话方向："通往 spec 的路径总是经过文件系统。"
Armin Ronacher: What Actually Is Plan Mode? ↗

为什么"接力到新会话"有效（证据）

  • 逐字 vs 隐含假设：同一会话里 Claude 携带写 spec 时的隐含假设，会停止逐字读 spec；新会话强迫它像新工程师一样从头、逐字读。〔buildthisnow〕
  • 成功率：没有 spec 文件，复杂功能首次成功约 1/3；四阶段（interview→spec→新会话→验证）可到接近 100%。（来自教程站 buildthisnow，非官方，仅供参考）
  • 上下文是第一约束：把长任务做成"接力"而非无限堆积——这恰是单会话蛮力（如 Willison 那次被自动压缩 16 次）的反面。〔官方 BP + 真实样本对照〕

怎么用这页对齐需求：大功能（T3 及以上）默认走形态 A——先用访谈 prompt 把需求挖透写成 SPEC.md（自包含、含验收），/clear 或新会话只读它实现、在 tasks.md 更新状态、用测试//goal 收口。plan mode（形态 B）适合"审一眼再动手"的中等改动，但别误当成跨会话接力。
