Agent 与 Eval实践补充2026-08-17

DeepSeek Harness Skills · 01

dsh-code-review
不是查格式，而是查“绿色 CI 仍可能漏掉什么”

这是 DeepSeek Harness 的 PR 语义审查入口。它先固定真实 base/head 与变更范围，再把评审者引向生命周期、接口两端、能力归属、执行点强制、状态发布、真实入口、测试强度、文档和 Agent Note，而不是把 review 退化成 lint 与覆盖率复述。

核验日期：2026-08-17 · 仓库 master：47f943859bef60e4160492346772ded9b24f765a · 直接来源：当前 SKILL.md、关联 AGENTS、测试策略、防御性模式、prose skill、Agent Notes 与 change-scope 决策。

最短结论 它是“评审判断标准加载器”，不是自动代码扫描器。

真正执行评审的仍是 Agent：读 PR、读上下文、追调用链、检查状态与测试，再按证据报告缺陷。skill 的价值是把仓库积累的高价值失败模式装进这次 review。

重要边界 它不会自动替作者跑完所有检查，也不会自动批准或合并 PR。

change-scope 只报告路径与 Git 层；CI 负责机械门禁；语义正确性、证据是否充分以及是否阻塞仍由评审者判断。

1 · 它什么时候触发？

metadata 的触发描述非常窄：审查 deepseek-harness 仓库中的 Pull Request。它不是通用 review skill，也不是作者写完代码后的 pre-push 流程。

需要可读取的 PR 或准确 base/head、仓库 checkout、PR 意图与关联 Agent Note。没有真实比较范围，就不能开始可靠审查。
适合行为、插件、生命周期、并发、权限、模型可见文本、文档、测试或跨包约定发生变化的 PR。
不等于格式检查、全量测试脚本、自动修复器、合并机器人、翻译工作流，或“一条规则命中就否决设计”的政策引擎。
官方逐字“This skill is guidance, not a complete checklist.”这项 skill 提供指导，而不是一份完整检查清单。— dsh-code-review

2 · 一次 review 实际怎样开始？

0 · 核实远端事实

获取 PR 当前 base 与精确 head

不能信旧报告，也不能用“当前分支的 upstream”猜 base；stacked PR 可能指向另一个 feature branch，PR retarget 或合并 base 后比较范围还会变化。来源：change-scope Agent Note。

1 · 生成事实范围

运行 change-scope

pnpm --silent run change-scope --base <verified-base-ref> --head <verified-head-ref> 输出版本化 JSON：解析后的 base/head/merge-base，以及 committed、staged、unstaged、untracked 四组路径。

2 · 读取规则和设计

加载适用的 AGENTS、上下文代码与 Agent Note

评审者不只看 diff；还要读接口另一端、所有当前消费者、所属插件/服务、相关 README、测试和决定来源。Agent Note 是设计讨论的证据，不是不可质疑的否决票。

3 · 先过硬阻塞项

确认同一个 PR 没缺必要伴随物

新 prose、代码对应文档、核心类型参考、注册清理、语义 invariant 与必要验证证据，是 skill 明列的 6 类 blocking requirements。

4 · 做人工语义检查

追行为，而不是数文件

检查生命周期竞争、取消与 dispose、执行点是否真正强制、派生状态是否从真源更新、上限是否覆盖完整结果、测试是否走真实入口并真的能在回归时失败。

5 · 输出最小而有证据的 findings

缺陷、位置、影响、证据四件套

局部问题贴最小 diff 行；跨切面设计问题放 PR 级评论；blocker 与 suggestion 分开；绿色门禁已经强制的问题不重复制造噪声。

3 · change-scope 到底解决什么？

它解决的是“我正在审什么”的事实问题，不解决“这些改动对不对”的判断问题。

它提供为什么重要它刻意不做
输入 base/head 与解析 SHA让错误 base 可见，避免 silently 审错范围不猜 base、不 fetch、不查询 GitHub
唯一 merge basestacked branch 与普通分支使用同一事实模型不决定 stack 策略
committed paths显示 merge-base 到 head 的提交改动不解释路径背后的行为影响
staged / unstaged / untracked避免本地脏层漏出审查视野即使 --head 指向其他 commit，也不把脏层伪装成该 commit
严格 UTF-8、NUL 分隔路径避免路径被错误合并或损失遇到无效路径字节直接失败，不返回有损报告
关键限制：改了一个配置文件，可能影响动态 Loader、子进程、provider 和快照；路径列表无法推导这些语义关系。因此官方决定明确拒绝“根据 changed paths 自动选择所有必要测试”。

4 · 六条硬阻塞要求

#阻塞条件评审者必须证明
1新增 prose 经过语义 reviewMarkdown、JSDoc、注释、prompt、description、diagnostic、UI 字符串内容正确、位置正确、覆盖完整；自动门禁不能证明语义质量。
2文档与代码一致配置、默认值、错误、wire 字段、事件和公共行为，同 diff 更新所属 README 与 JSDoc；删除实现旁白、测试复述和重复 rationale。
3核心类型文档一致主干或能力 seam 词汇变化同步更新所属 subsystem 页面与已有 type-equiv；内部类型无需强造 catalog 项。
4注册贡献能清理每个新 registry contribution 都有 dispose/HMR 测试，销毁 fiber 后贡献确实消失。
5invariant 真正在查运行关系./invariant 应检查包能观察到的事件流或可变数据关系；不能拿服务存在、插件 metadata 或固定纯例子冒充 runtime invariant。没有合理关系时，带具体理由的空 installer 可以接受。
6必要证据存在作者运行了与 diff 对应的窄本地检查，CI 覆盖穷举矩阵；review 继续查两者都无法发现的语义缺口。

逐条原文：Blocking requirements。

5 · 十五类人工检查，可以压缩成六个问题

接口真的闭合吗？追接口两端、错误、取消、所有权、dispose；确认通用 service 没被单一 consumer 污染，也没有为一个内部调用者扩张公共 API。
生命周期会不会撒谎？异步 setup、回调、进程和 teardown 要查 publication 前 race、await 中取消、回调隔离、完全 detach 与 quiescent disposal。
限制真的执行了吗？schema 隐藏、prompt 指示和 wrapper 都不是安全强制；必须追到实际执行操作，并测试可绕过的直接或替代调用路径。
状态来源唯一吗？分清 borrowed/owned 值；通知、cache、prompt、UI、replay 和 query view 必须从同一个成功提交点与权威来源派生。
测试证明现实吗？走发布后的 Loader、bin、worker、ACP 或 subprocess；对外重读文件/事件/状态；加入能通过真实 runner 失败的 negative control。
对模型和读者诚实吗？检查实际 prompt、tool schema、result、diagnostic 与 snapshot；implemented Note 写当前事实；双语内容人工核对意义与术语。
官方逐字“Coverage is necessary but not evidence that the scenario is correct.”覆盖率是必要条件，但不能证明测试场景本身正确。— dsh-code-review · Test strength

6 · 一个合成 PR 示例：新增 maxOutputBytes

实践补充下面不是仓库真实 PR，而是用该 skill 的规则演示 review Agent 会怎样思考。

只看 diff 可能得到dsh-code-review 会继续追问可能形成的 blocker
新增配置字段并在函数入口判断长度完整返回值是否还会被 wrapper、metadata 或编码扩大？字节还是字符？限制位置看不到最终 emitted result；多字节文本可绕过预算。
tool schema 不再暴露超限操作直接调用 executor 是否仍能执行？其他 caller 能否绕过 schema？规则只在展示层，不在做决定的执行点强制。
单元测试达到 100% coverage测试是否验证 tiny/exact/oversized/multibyte？是否走真实 Loader/worker？断言只是复述实现，回归经过发布入口时仍不会失败。
新增 callback 在结束时通知异常是否隔离？dispose 是否等待子进程完全停止？晚到通知是否泄漏？teardown 只发送 kill 没 await done，留下遗留进程或晚到状态。
README 写了新默认值JSDoc、config catalog、diagnostic、Agent Note 和双语对侧是否一致？代码、对外约定与长期决策记录互相矛盾。
[blocker] Limit is enforced before the final wrapper is added Location: packages/.../src/result.ts:88 Defect: maxOutputBytes measures payload only; the public result adds metadata afterward. Impact: callers can receive a value larger than the documented hard limit, and multibyte text is under-counted. Evidence: the executor's final serialization occurs at ...:126; existing tests cover ASCII below the limit only.

7 · 自动化与人工判断怎样分工？

层负责什么不负责什么
change-scope确定 Git 拓扑、SHA 与四层路径集合不选测试、不理解行为、不判断风险
hooks / CI类型、lint、覆盖率、重复、包结构、文档链接与格式等机械承诺不证明 prose 准确、设计归属合理、测试场景正确
review Agent读上下文、追接口和生命周期、验证 denial 与状态来源、判断证据强度不应重复绿色门禁已经给出的低价值噪声
人类维护者裁决设计争议、产品取舍和风险接受不需要手工复做每个可机械执行的门禁
官方逐字“Agents follow enforced gates far more reliably than prose conventions.”Agent 遵守可执行门禁，比遵守纯文字约定可靠得多。— Mechanical quality gates over prose guidelines

8 · 它与其他 skills 的关系

对象关系是否由 review 自动完整执行
dsh-prose-standard所有新增或修改 prose 的语义审查标准需要使用，但 scope 限于本 PR prose
dsh-pre-push-checks作者侧选择并运行提交前证据；review 验证证据是否与 diff 匹配不会把作者流程整套重跑
dsh-doc-standards文档位置、预算、结构、门禁与 slop audit作为文档真源被引用，按 diff 需要使用
dsh-translate-docs扩展翻译工作流不会；只有用户明确调用才运行
Agent Notes提供 why、放弃方案与验证要求读取相关记录；不同意见进入设计讨论，不自动 veto

9 · 这套 review 的真正优点

把历史事故变成审查记忆并发、dispose、Loader 入口、callback 隔离、状态发布等不是抽象最佳实践，而是仓库沉淀的真实缺陷类别。
减少“CI 绿所以没问题”它明确把覆盖率、配对 hash 和门禁定位为必要但不充分的证据，强迫评审者验证场景和外部现实。
约束公共 API 膨胀同时检查 consumer 行为泄漏到 service，以及只有一个内部调用者却扩张通用 service 的反向问题。
提高 findings 信噪比优先 correctness、lifecycle、security 和必需行为；允许只报告一个证据充分的 blocker，而不是堆积风格 nit。
让 review 可随仓库演化skill 是导航层，具体规则留在 AGENTS、测试文档、Agent Note 和 prose standard；真源更新后 review 会跟随。
适合 Agent reviewer机械范围报告缩小搜索空间，明确的 defect/location/impact/evidence 输出约定降低模型生成泛泛意见的概率。
官方逐字“A short review with one substantiated blocker is better than a list of nits.”一份只有一个证据充分 blocker 的短 review，也胜过一串琐碎意见。— dsh-code-review

10 · 局限与成本

局限实际影响可怎样缓解
认知负荷高49 行 skill 会路由到多份长文档；陌生 reviewer 首次成本明显按 change-scope 和触碰领域只读相关真源，不做全仓漫游
依赖模型判断它明确不是完整 checklist，不同 reviewer 深度可能不同保持 blocker 清单机械明确，用真实 failure examples 持续校准
没有自动停止条件复杂 PR 可能无限追调用链以 PR 意图、当前消费者和可观察行为为边界；额外重构另开任务
base 必须人工核实输入错仍可能审错范围，只是 SHA 会让错误可见从 live PR metadata 获取 base/head，retarget/merge 后重跑
高度仓库特化seam、Cordis、Agent Note、snapshot tier 等规则不能原样搬到普通项目复用结构而非术语：范围事实 → 硬阻塞 → 领域 bug 类 → 证据报告
不会替代产品判断Agent Note 与代码一致也可能是错误产品决定把与 Note 的分歧升级为设计讨论，而非自动接受或自动否决

11 · 如果搬到你自己的 AI Coding 工作流

最值得复制的不是 15 条 DeepSeek 专有检查，而是三层分工。

事实层固定 task/PR、base/head、变更文件、脏工作区和关联决定；不让 Agent 猜评审范围。
机械层能写成脚本的承诺全部门禁化；review 不重复 lint、类型和格式输出。
语义层为你的项目维护 5–10 个真实 bug class：权限执行点、事务提交点、并发取消、真实入口、世界状态验证等。
请审查 PR #123： 1. 从 live PR metadata 核实 base/head，不使用缓存结论。 2. 生成 committed/staged/unstaged/untracked 范围报告。 3. 读取本 PR 涉及目录的 AGENTS、设计记录和公共契约。 4. 先查必须伴随的 docs/tests/migrations，再追接口两端、生命周期、权限执行点和状态真源。 5. 只报告可证实的问题；每条包含 defect、location、impact、evidence。 6. 将 blocker 与 suggestion 分开，不复述绿色 CI 已强制的项目。
与前文 Task-first 思路的衔接：Task Record 管“为什么要做、当前做到哪”；dsh-code-review 管“这次交付是否真的满足约定”。它应挂在 Task 的 Review 阶段，而不是代替 Task 状态记录。

12 · 证据强度与版本说明

可直接确认

当前 skill 有 7 组真源、6 条 blocking requirements、15 类 manual checks；首段要求核实 live base/head 并运行 change-scope；报告格式要求 defect、location、impact、evidence。

历史归纳

本地完整 Git 历史显示该文件自 2026-06-13 创建后约有 40 次相关提交，持续吸收 prose、invariant、change-scope、Agent Note 和 subsystem 规则。提交次数是 Git 历史统计，不是仓库文档的自我声明。查看：文件提交历史。

不能确认

公开仓库没有每一次内部 review 的完整会话，因此无法统计该 skill 实际抓住多少缺陷、由哪个模型执行、是否每次都被自动加载，或人类如何裁决每一条建议。

主要来源

  • dsh-code-review / SKILL.md：触发、真源、硬阻塞、15 类人工检查与 findings 规则。
  • Explicit change-scope report：为何必须显式 base/head，以及报告做与不做什么。
  • Root AGENTS.md 与 packages/AGENTS.md：仓库和包级约定。
  • Defensive patterns：并发、回调、子进程与 dispose 缺陷类别。
  • Testing policy：测试层级、真实入口、世界状态验证与 snapshot 要求。
  • dsh-prose-standard：prose 覆盖与语义判断。
  • Agent Notes：决定记录与生命周期。
  • Mechanical quality gates：自动门禁与人工 review 的分工依据。
最终判断：dsh-code-review 的价值不在“多列一些检查项”，而在把 review 从 diff 表面带到真实执行语义：先固定范围，再让机器挡住机械错误，最后让 Agent 只报告对 correctness、lifecycle、security 和必需行为真正有影响的缺陷。
