Agent 与 Eval实践补充2026-08-17

DeepSeek Harness Skills · 02

dsh-find-simplifications
不是自动精简，而是先证明“什么值得删”

它把“找点可以简化的地方”变成一次仓库级减法审计：扫描多个领域，区分生产与非生产消费者，核对既有设计理由，证明收益与代价，然后把大候选写成 proposed Agent Note、小候选写成局部 TODO；证据薄弱的想法直接淘汰。

核验日期：2026-08-17 · 仓库 master：47f943859bef60e4160492346772ded9b24f765a · 当前文件 146 行（96 LOC）、11 个章节；自 2026-06-20 建立后有 16 次相关提交。

最短结论 它是“技术债候选发现与立案规范”，不是重构执行器。

Agent 的主要工作是搜代码、读调用点、判定所有权和生命周期、查 Agent Note，再输出可实施的简化提案。真正删代码通常发生在后续 Task / PR。

与你的思路最相关 它有证据标准，却没有任务状态模型。

没有 task id、负责人、进度、重试、依赖或全局队列。Agent Note 记录“为什么值得这样改”，并不记录“现在做到哪一步”。

1 · 什么请求会触发它？

仓库减法审计寻找死 API、重复表示、投机功能、过度防御、重复生命周期机制、只服务测试的包或产物。
整理 Agent Notes合并已被完全取代的决策记录、保留部分取代的记录、归档低未来价值的已实现记录。
吸收另一个 PR从 sibling branch 中筛出有价值且不重复的提案或 TODO，按其独立贡献合并进当前 PR。
官方逐字“This skill helps turn a broad ‘find things to simplify’ request into evidence-backed Agent Notes that remove or collapse existing harness surface area.”它把宽泛的“找可简化项”请求，转成有证据支持的 Agent Notes，用来删除或折叠现有 Harness 表面。— dsh-find-simplifications

2 · 一次完整执行会怎样进行？

0 · 固定审计范围

确认是全仓、某个领域，还是另一个 PR 的候选

用户若要求广度或多个候选，skill 明确要求按领域并行调查；若不能使用 subagent，则由一个 Agent 模拟相同覆盖面。它还要求从最大的生产代码增量开始，而不是只跑一遍未使用符号工具。

1 · 先读“不能随便删”的理由

加载 AGENTS、architecture、defensive patterns、testing 与 Agent Notes

双 LLM adapter、双持久化 backend 等被视为有意设计。看起来重复不等于可删；候选必须用新证据击败已经记录的架构理由。

2 · 广泛发现候选

扫 agent loop、ACP/UI、LLM/tools、shell、packages/tests 等领域

关注死接口、镜像状态、无消费者 seam 方法、只服务测试的包、无产品 owner 的通用能力、手写基础设施和保护无用 API 的测试机制。

3 · 给每个候选做消费者分类

生产、非生产、模糊三类分别核实

先用 rg 搜 symbol、wire string、config key 和调用形式，再读调用点。knip 只能辅助，不能识别动态事件、Cordis Loader、示例 smoke path 或公共接口承诺。

4 · 审计信任和生命周期

解释每个 copy、freeze、validator、promise、sentinel 与 disposer 的所有者

如果多个机制只是镜像同一个存活或 settlement 事实，尝试折成一个 transaction/controller；但同步发布回滚、callback containment、first terminal outcome、进程所有权和 dispose-to-quiescence 等保护必须保留。

5 · 证明、降级或否决

不是“发现复杂”，而是证明维护成本超过收益

存在生产 caller、触碰受保护设计、只制造无收益 churn，都会让候选被拒绝；正确但很小的项降级为局部 TODO/FIXME/XXX。

6 · 把结果路由到不同产物

大决策进 Agent Note，小清理进注释，旧记录按规则合并或归档

每个 durable proposal 单独立 proposed Agent Note；写清 Problem、Proposal、放弃什么、Acceptance criteria 与 Risks。审计仍在扩展时使用 draft PR。

7 · 校验和 PR 汇报

对文档型产物运行门禁，并明确没做什么

至少执行 pnpm run doc-sync、pnpm run lint、git diff --check；PR 报告新增、合并、保留、删除多少记录，调查了哪些区域、刻意排除了什么。

3 · 什么才算“强候选”？

信号必须补的证据为什么可能值得删
公共方法、事件、配置、helper 没有生产消费者搜索定义、调用形式、wire string、动态注册、Loader 与示例路径删除真正缩小公共 API、文档和测试责任
只有 tests/docs 使用证明这些测试没有保护真实入口或兼容承诺测试可能只是在固定过去的设计，而非必要行为
两个状态表示同一个事实找到各自 producer/consumer、提交点与恢复路径单一权威状态可删除同步与失配机制
每个实现都必须实现、但没人调用的 seam 方法检查所有 provider 和 consumer，不只看一个包缩小接口后每个实现都少维护一份空泛能力
无产品 owner 的投机通用能力证明配置、UI、runtime scripts 和产品文档都没有真实入口未来可能性不再让当前系统承担生命周期成本
手写 parser/retry/glob/diff核对 package 健康、语义覆盖、传递依赖和剩余 glue外部依赖或 Node builtin 可删除实现、专用测试和文档
官方逐字“Prefer a few well-proven candidates over a pile of thin guesses.”宁可保留少数证据扎实的候选，也不要堆一批单薄猜测。— dsh-find-simplifications

4 · 哪些“看起来能删”其实证据很薄？

只跑一次 knip静态工具看不到动态事件名、配置 Loader、公共接口和某些 example/runtime 路径。
“这里看起来很复杂”复杂可能来自并发结算、进程回收或 crash recovery；没有所有权图就不能证明可合并。
只删一个 typo这是直接机械修改，不值得新建一篇 durable Agent Note。
删除平行 backend仓库明确保护双 adapter、双 persistence 设计；重复实现可能用于证明 seam 真正可替换。
测试通过所以必须保留根规则是“tests describe behavior, not correctness”；测试可能只是历史妥协的产物。
换依赖但 wrapper 一样复杂如果只是搬动复杂度而没有净删除，依赖替换不算 simplification。
官方逐字“A wrapper that relocates the same complexity is not a win.”一个只是把相同复杂度搬到别处的 wrapper，并不算收益。— Hand-Rolled Code Versus A Dependency

5 · 最重要的分流：最后到底产出什么？

发现产物是否已经完成代码简化
非局部、会改变公共行为、架构或多个包.agents/notes/proposed/simplification/yyyy-mm-dd-topic.md，并带中英与一致性记录没有；只是形成可评审设计提案
小而局部、行动明确FIXME、TODO 或 XXX，带稳定 smell tag没有；只是留下代码旁待办
旧 Agent Note 被完全取代把独有理由转移到当前 owner，修链接，成套删除旧中英 note 与 sidecar简化了决策文档，但不一定改变代码
已实现记录未来价值低调用 dsh-archive-agent-notes，冻结为 archived triplet只缩小活跃决策语料
存在生产 caller 或证据不足拒绝或降级候选，记录排除范围不改；这是正确结果，不是失败
所以它不是普通“代码任务”。一次成功执行可以得到 0 个 Agent Note，因为所有候选都被证据否决；也可以得到多篇 proposed Notes，但这些仍需要后续选择、实现、测试和 review。

6 · 仓库里的真实正例：删除 mutable session summary

这篇已实现 Agent Note 展示了该 skill 所追求的证据形态，而不是泛泛地说“metadata 太复杂”。

审计发现证据最终减法
SessionPersistence.update() 是死 API全仓没有生产 caller；命中的 .update( 是 hash 或测试从抽象 service 和全部 backend 删除该方法
firstPrompt 没有生产读取title 已来自 durable session/title，picker 从未实现删除 SessionSummary 与 SessionMeta
两个 backend 为未来缓存付出不同持久化成本JSONL 维护 sidecar，SQLite 维护列与 append 更新删除 sidecar、列、更新逻辑和配套 contract tests
未来需要的多数信息可以从日志推导first prompt、recency 已在 append-only log 或 header 中把真实产品需求出现之前的缓存视为 YAGNI

来源：Drop the mutable session summary。

7 · 另一个正例：不是删除 backend，而是合并重复生命周期

JSONL 与 SQLite backend 都被保留，因为“双实现”证明 persistence seam 可替换；真正被折叠的是两边重复、且持续接收相同 bug fix 的写入编排。

重复成本per-session state、adoption、prefix read、write-behind、serialization、HMR seed 与 dispose drain 在两端重复。
简化方式提取 backend-agnostic PersistenceCoordinator，backend 只实现窄 storage hooks。
保留差异JSONL byte offset 与 SQLite seq 作为 opaque torn marker，各自保留真实存储语义。

来源：Shared persistence write coordinator。

8 · 为什么先读架构？“包多”不等于“过度设计”

Capability seam 是受保护的设计理由

DeepSeek Harness 将一个可替换能力拆成 Service Definition、Service Provider、Consumer 三种角色。这样本地 executor 可以被 sandbox/remote provider 替换，而不改变模型看到的 tool schema。这个拆分确实增加 package.json、tsconfig、README 和注入 wiring，但换来独立演化。

skill 的判断标准不是“文件更少”

如果三个角色不会独立演化，预先拆包可能是候选；如果已经有多个 provider 或明确的产品替换需求，粗暴合包会损坏 seam。必须比较实际消费者、演化速度和 Agent Note 里的 alternatives。

来源：Capability seams、Architecture。

9 · 它和 Review、Task、Agent Note 的关系

对象输入主要问题输出
dsh-find-simplifications仓库、领域或 sibling PR哪些现有表面成本大于收益？候选取舍、proposed Notes、局部 TODO、记录合并
dsh-code-review一个具体 PR 的 base/head 与 diff这次交付是否有 correctness/lifecycle/security 缺陷？带 defect/location/impact/evidence 的 findings
Agent Note一个非平凡设计决定为什么这样做，放弃了什么？可长期维护的决策记录
Task / Sprint要完成的工作与验收条件谁做、做到哪、何时结束？状态、步骤、依赖、结果和关闭条件
它没有取代全局任务记录。find-simplifications 只负责“发现与立案”；候选是否进入 roadmap、什么时候实现、谁负责和是否验收，仍应由 Issue / Task 系统管理。

10 · 优点与真实代价

优点代价 / 风险
把“凭感觉重构”变成 production-consumer 证据链全仓搜索、读调用点和画生命周期图很耗上下文
允许行为略有变化，只要新行为合理且更易解释“合理”仍依赖 Agent 与 reviewer 判断，不是机器定理
主动保护有理由的复杂性，避免误删双 backend/seam既有 Agent Note 可能形成路径依赖，新证据要付出更高举证成本
把依赖替换纳入正当 simplification需要持续评估外部包健康、供应链和残余 glue
候选可以被拒绝；不追求数量没有显式时间预算或停止条件，广度审计可能持续扩张
区分大设计提案与小局部清理大量 proposed Agent Notes / TODO 仍可能制造新的文档债
官方逐字“Use a draft PR while the survey is still expanding; mark ready only when the candidate set, review responses, and validation are settled.”调查仍在扩展时使用 draft PR；只有候选集合、评审反馈和验证都稳定后才标记 ready。— Validation And PR Hygiene

11 · 如果按你的 Task-first 思路改造

最值得保留的是证据标准；最该调整的是“发现后立刻写多个 Agent Notes”。先让 Task 管候选漏斗，再把被接受的长期决定提升为 Agent Note，会更符合你的全局记录思路。

Task: Simplification Audit #042 Scope: session persistence + replay Budget: 2 hours / 最多 5 个候选 Acceptance: 每个候选必须有 production/non-production consumer 证据 Candidate states: DISCOVERED → PROVEN / REJECTED → SELECTED → IMPLEMENTING → VERIFIED Promotion rule: - 小局部清理：直接成为子任务 - 非平凡设计：SELECTED 后才写 proposed Agent Note - 没进入本轮：保留证据摘要，不制造长期 Note - 实现 PR：关联 Task + Agent Note，交给 code-review skill
Task 是总账保存范围、预算、候选状态、选择结果、实施进度和验收。
Agent Note 是设计附件只记录被选中且值得长期保留的 why、trade-off 与 reintroduction condition。
PR 是交付证据代码、测试、文档与 review findings 证明选中的简化真的完成。

12 · 最终判断

这个 skill 适合作为周期性“减法发现模式”，不适合作为日常任务主干。

它解决的是大型 AI coding 系统常见的一个问题：Agent 很容易不断添加抽象，却很少有制度化流程去证明某个表面可以安全删除。它用消费者证据、所有权图、既有决策和净删除来提高减法质量。

但你的不适感有根据：它把 durable proposal 放在 Agent Note 树和 draft PR 中，没有一个统一 Task Record 串起发现、选择、实施、验收。若照搬到你的系统，应把它嵌入 Task 的“技术债发现”阶段，而不是让 Agent Notes 充当 backlog。

主要来源

  • dsh-find-simplifications / SKILL.md：触发、候选标准、调查领域、证明与否决、输出和验证。
  • Root AGENTS.md：pre-release、测试不是正确性真理、Agent Note 与架构约定。
  • Architecture：插件树、事件域与 capability seam 背景。
  • Defensive patterns：生命周期与并发机制不能凭表面复杂度删除。
  • Agent Note rules：lifecycle、classification、full/partial supersession 与文件结构。
  • Drop mutable session summary：零生产消费者驱动真实删除的案例。
  • Shared persistence coordinator：保留双 backend、折叠重复生命周期的案例。
  • Dependencies over hand-rolling：净删除、健康度、语义适配和受保护 seam 标准。
  • TODO marker semantics：FIXME / TODO / XXX 的优先级。
  • 文件提交历史：建立与后续演化记录。
一句话：dsh-find-simplifications 管“什么值得成为减法提案”，Task 管“这项减法什么时候、由谁、怎样完成”，dsh-code-review 管“完成的减法是否真的安全”。三者不能互相替代。
